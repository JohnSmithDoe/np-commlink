# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`np-commlink` — Ionic 8 + Angular 21 (standalone, zoneless) + Capacitor 8 app. It is the **merge of two apps**: `np-timetracker` (time/office tracking, the structural + visual base) and `np-kitchen-bot` (shopping / storage / tasks / globals grocery lists, grafted in as independent features). One Shadowrun/cyberdeck look throughout. Ships as a web app (PWA) and an Android APK.

The current architecture (who talks to whom, and why) lives in **`docs/project-summary.md`** — read it before touching the grocery subsystem. The merge decision log and refactor history are in the git commit log; open/deferred work is in `docs/project-summary.md` §12.

> We work trunk based. so only on the main branch. if you must use a worktree instead of a branch but try to just keep up with other changes and work on the main.

## Commands

- `pnpm start` — dev server (`ng serve`). `pnpm run build` — prod web build (`www/browser`).
- `pnpm test` — Vitest via `@angular/build:unit-test` (one-shot). `pnpm run e2e` — Playwright (`e2e/`, port 4321).
- `pnpm run lint` — lint (flat `eslint.config.js`: angular-eslint + @ngrx + Sheriff + **`ionic-a11y`,
  this project's own rule set in `eslint-rules/`** + prettier). Both it and CI lint
  `src/**/*.{ts,html}`: most of the a11y set and the no-domain-vocabulary gate live on `*.html`, so a
  `*.ts`-only glob runs a strict subset of the gate. **Two** blocks still set
  **`no-restricted-syntax`** on the same templates (the two i18n vocabulary gates), and flat config
  _replaces_ a rule's options rather than merging them, so a new selector must be spread into both or
  it is silently dropped wherever a later block matches — check with `eslint --print-config <file>`,
  never with a passing suite (`docs/project-summary.md` §10). That footgun is exactly why the a11y half
  is a rule set now: a rule _id_ cannot be shadowed the way a rule's options can.
- **`eslint-rules/`** — the mechanical half of `docs/ionic-a11y-practices.md`, eight rules named for the
  R-numbers there (`ionic-a11y/icon-is-hidden-or-named`, …). Plain CommonJS on purpose:
  `@angular-eslint/builder`, which `ng lint` and CI invoke, resolves only `eslint.config.{js,mjs,cjs}`,
  so a TypeScript rule set would need `eslint.config.ts` + `jiti` and would make the lint target stop
  finding its config. It needs no dependency either — the template parser services hang off
  `context.sourceCode.parserServices`. The rules export nothing but `rules`; **which files each one
  applies to is decided in `eslint.config.js`**, next to every other gate.
- `pnpm run i18n:extract` — rewrite **both** bundles (`public/i18n/{de,en}.json`) from the
  `marker(...)` literals, **`--clean` included**, so a dead key is pruned rather than removed by hand.
  That works only because **no key is composed at the call site any more**: every family that used to
  be built from a template string is a `marker(...)` const — `IDeckEntry.labels`/`.metricKey` on the
  catalog entry, `DECK_CHROME_LABELS`/`DECK_MODULE_LABELS` (`commlink/model/deck.labels.ts`),
  `UNIT_LABEL_KEYS`. Composing a key again is what silently makes it prunable; the acceptance test is
  that running the script leaves `git diff public/i18n/` clean. Three flags are load-bearing:
  `--format-indentation '  '` + `--trailing-newline` make the tool's bytes match prettier's (the two
  writers agree instead of being mediated by the pre-commit hook), and the alias `-fi` must **never**
  be used — with two outputs yargs reads it as clustered `-f -i` and the run dies with
  `Unknown format: json,json`. Plan and measurements: `docs/project-summary.md` §9.
- `pnpm run build:android` — prod web build + `cap sync android` + the postsync patches.
  `pnpm run apk:debug` / `apk:release` chain a Gradle `assemble` onto it; `pnpm run open:android`
  opens Android Studio. `sync:android` is the sync half alone (skip the Angular rebuild).

> **Testing philosophy** (inherited from timetracker). Lean, not exhaustive. Two layers:
>
> - **Vitest unit — pure logic** (`*.spec.ts`): utils, pipes, reducers, selectors (via `.projector(...)`). No `TestBed` where a plain call suffices.
> - **Vitest unit — component class logic** (`*.component.spec.ts`): `TestBed.createComponent(...).componentInstance` + `provideMockStore()` + `provideZonelessChangeDetection()`. **Do not `detectChanges()`** — jsdom doesn't run Stencil, so `ion-*` are inert; rendered-DOM assertions belong in e2e.
> - **Playwright e2e**: real-browser behavior. Scope content assertions with `#main-content` (the side menu is a sibling list of the same destinations) and use **hash routing** URLs (`/#/groceries/storage/_storage`).
>   Five Ionic locator traps cost a red spec every time they are rediscovered — a spec that ignores them passes alone and fails after an SPA navigation:
>   - **Scope controls to the page component** — every page's selector is `app-page-<x>` (`app-page-recipes`, `app-page-storage`, `app-page-trackplay-games`), not just `#main-content`: the router outlet keeps previously-visited routes mounted (the `lazy ≠ unloaded` rule, seen from the DOM), so a sibling page's identical "Hinzufügen" button is still there.
>   - **An `<ion-modal>`/overlay teleports to the app root**, so it is _outside_ that page scope — key a presented dialog off its **title**, never off its wrapper element. Three DOM facts make the tempting scopes wrong, all verified on `/groceries/storage/_storage`: presenting **moves** the `ion-modal` to `ion-app` and leaves an `overlay-hidden` twin behind inside the wrapper (so the wrapper element matches _two_); a single list route mounts **five** `ion-modal`s (the item dialog, its category picker, the date picker, …); and Ionic puts **no `role="dialog"`** on `ion-modal`, so `getByRole('dialog')` matches nothing. `.show-modal` narrows to what is presented, the title to which one — `e2e/groceries/storage.e2e.ts` has the helper.
>   - **Click an `ion-select` host**, not its accessible button: the shadow `part="inner"` swallows the click.
>   - **Re-entering a route mounts the page a _second_ time** — the same `app-page-<x>` then matches twice and every row locator inside it is a strict-mode violation (`:visible` does _not_ help; the stale instance is not `display:none` at assert time). A spec that bounces between two routes should navigate with `goto` **+ `reload()`**, which collapses the outlet to one instance and makes every assertion a cold read of persisted state besides (`e2e/commlink/deck-config.e2e.ts`).
>   - **A bare `ion-toast` is not unique** — the shell mounts the service-worker update prompt, and an inline overlay is in the DOM whether presented or not, so `page.locator('ion-toast')` matches two. Narrow with **`:not(.overlay-hidden)`** (the same class as the `ion-modal` twin); `e2e/trackplay/players.e2e.ts` is the worked example. The general rule: an always-mounted overlay makes every element-name locator for that overlay ambiguous **app-wide**, so adding one to the shell edits every spec's namespace.
>
> Shared test infra is at `src/app/@shared/testing/` (`test-data.ts` deterministic factories, `test-providers.ts`, `dom.ts`), reachable only from `*.spec.ts` (Sheriff `type:testing`). NgRx **effects stay RxJS**. Rely on Vitest `globals:true` — do **not** `import … from 'vitest'`.
>
> **`data-testid` — the locator contract.** Anything a spec locates that is *not* already a
> contract carries a `data-testid`: Ionic element names (`ion-note`, `ion-toggle`), tag names
> (`h2`), CSS classes (`.cl-node__badge`, `.cash-empty`, `.status-bar`) and — worst — icon names
> (`ion-icon[name="add"]`) and translated text in a combinator all say something about styling or
> iconography rather than identity, so a re-theme or an Ionic upgrade can redden a green suite with
> no behaviour change. Specs read them via `getByTestId`/`queryByTestId` (`@shared/testing/dom`,
> Testing-Library semantics: get throws, query returns null) and Playwright's own `getByTestId`.
> Four rules, each of which the sweep proved the hard way:
>
> - **A component element name is already a contract** — `app-page-cash`, `app-tracking-item`,
>   `app-text-item` are declared in `@Component` and are used directly. A second name for the same
>   element is one more thing to keep in sync, not more safety.
> - **Never compose an id at the call site.** `'row-' + item.id` in a template and
>   `getByTestId('row-milk')` in a spec share no literal, so neither half is greppable and the "which
>   elements do tests depend on" signal is gone — the same failure mode that makes a composed i18n
>   key invisible to `i18n:extract --clean`. A repeated row carries the static `list-row`; *which*
>   row comes from user-visible content (`filter({ hasText })`), never from a domain id.
> - **An id cannot disambiguate two instances of one template.** Re-entering a route mounts the page
>   a second time and both copies carry every id, so a row locator is a strict-mode violation — the
>   remedy stays `goto` + `reload()` (and the reload must follow a URL-awaiting helper like
>   `gotoFeature`, since a hash navigation is same-document and reloading too early reloads the route
>   just left). Likewise `.nth(i)` is correct where the index *is* the semantic (a score grid's player
>   column), and only a smell where it stood in for an ambiguous match.
> - **Add an id only where a spec locates something today.** `pnpm run verify:testids` decides the two
>   directions a script can — an id no spec references (dead, and no test can catch it) and a spec
>   referencing an id no template declares (a locator that can never match). It caught 13 speculative
>   ids on its first run. The third case, a spec that ignored the ids entirely, is **not** decidable
>   from the two file sets and stays a review matter.

## Code style — speaking code instead of comments

We use **speaking code instead of comments**. Only ever comment the **why** — never the **how**; the how must be cleanly readable from the code itself. Prefer **small functions with human-readable names**, written as prototype functions (**skeleton → execution**): the top-level function reads as the list of steps, each step a named call that a reader can descend into only if they care. If you feel the urge to write a comment explaining what a block does, extract that block into a well-named function instead. Keep comments to an absolute minimum — the only ones that earn their place are non-derivable rationale (a domain rule, a workaround for external behaviour, a trade-off someone would otherwise "fix").

## Architecture

> **⚠️ Re-domained (2026-07, branch `feature/ddd-refactor`).** The grocery subsystem was
> restructured by a DDD refactor: `shopping`/`storage`/`products` (was `globals`) are now
> features of a **single `groceries` domain** (`src/app/groceries/`); `tasks` is its own domain,
> sealed off the grocery engine via a `ListPageFacade` (`@shared/util/list/`); the shared page
> is the domain-blind `list-page` (was `grocery-list-page`); `notifications` and `commlink` no
> longer import any domain (inverted behind `@shared` `notify`/`dashboardTelemetry` contracts);
> and the grocery cluster + `tasks` are **lazy** (co-hydrated via a route resolver). Some
> descriptions below predate this — **`docs/project-summary.md` is the current, authoritative
> structure.**

Standalone app bootstrapped from `src/main.ts` (no `AppModule`). All providers (router, store, effects, Ionic, translate, storage) are wired in `bootstrapApplication(...)`.

### Folder layout (Hahnekamp-style, Sheriff-enforced)

Domain-first, sliced by type; every dir carries a `domain:*` + `type:*` tag (`sheriff.config.ts`).

```text
src/app/
  app.component.ts / app.routes.ts / app.providers.ts / app-title.strategy.ts   ← type:shell
    (no shell effects left — every orchestrator moved into its own domain's data/;
     app.routes.ts is a `path → loadChildren` table — every domain owns a
     routes/<domain>.routes.ts, tagged type:routes and sealed to its own domain)

  @shared/                                          ← domain:shared
    model/    ( app.types.ts [primitives] + one file per shared concern: base-item ·
                category · item-list · notifications · dashboard · settings ·
                app.consts.ts )                       testing/ (type:testing)
    data/     ( actions/ [dashboard · notifications — the two published contracts —
                          + item-list.actions.factory, the shared event map] ·
                effects/ [persisted-slice + item-list *.factory.ts — the effect builders] ·
                persisted-context.provider — the bounded-context descriptor ·
                boot-hydration.provider · module-hydration.resolver )
    util/     ( db/ [database.service · versioned · migrations] · list/ [list.utils ·
                list.selector · LIST_FACADE] · categories/ · charts/ ·
                item-dialog.service · theme.service · splash.service ·
                app-update.service + app-reload.service · pipes )
    ui/       ( base-item/ · categories/ · forms/ · page-header/ )
    feature/  ( list-page — the domain-blind page shell · edit-item-dialog + modal-dialog —
                the two dialog bases · edit-categories-page )

  commlink/ tracking/ office-time/ notifications/ barcode/        ← timetracker domains
    commlink/{data,model,testing}/ = the dashboard read-model + the deck catalog
      and its config slice (two eager slices, both commlink-owned)
  groceries/                                                      ← shopping + storage + products
  tasks/ cash/ trackplay/                                         ← one domain each
  settings/{data,feature}/                                        ← app-global settings (theme) — sealed, eager slice
  geist/{feature,model,util}/                                     ← GEIST — Chrome on-device-model console; NO data/ layer (holds zero NgRx state)
    groceries/feature/{recipes-page,edit-recipe-dialog}/ = SOYKAF, the recipe book
      (the `kitchen` domain is deleted — route path ≠ folder)
    cash/feature/ + trackplay/feature/ = the imperative edit modals (moved out of
      smart-ui, which cannot reach the shared BaseModalDialog)
```

**Inside every `<domain>/data/`** the files are sliced by NgRx role, so a multi-slice domain stays
navigable and all eleven data modules read the same way:

```text
<domain>/data/
  actions/      <slice>.actions.ts             ← one file per action group
  reducer/      <slice>.reducer.ts (+ .spec)
  selectors/    <slice>.selector.ts (+ .spec)
  effects/      <slice>.effects.ts, or <slice>-<role>.effects.ts once a slice has
                more than one (+ .spec)   ← only the domain's OWN effects;
                load/save/telemetry come from the descriptor
  <x>.facade.ts · <domain>.providers.ts · index.ts      ← the DI-facing root
```

**Two kinds of effects, and the casing tells you which.** A domain's hand-written effects are
`@Injectable` **classes** (`TrackingEffects`, `ShoppingEffects`); effects assembled from the shared
builders in `@shared/data/effects/*.factory.ts` are exported as **functional objects**
(`tasksListEffects`, `trackingListEffects`) — because NgRx dedups same-class instances across
injectors, so a shared _class_ registered in two lazy contexts would double-dispatch, while every
call of a builder gets its own identities. A role suffix only appears where a slice owns several
effects files (`tracking-list` · `-message` · `-notifications`); a slice with one file is just
`<slice>.effects.ts`, and an _empty_ effects class is not a placeholder — it is dead code (the
`ProductsEffects`/`TasksEffects` shells were deleted).

**`data/` holds no pure logic.** A `<slice>.utils.ts` that imports no `@ngrx` is not data — it is
`util`, and it lives in the domain's own **`<domain>/util/`** (`405928e`). `data → util` is a
downward edge Sheriff already permits, so the reducer/selector/effect that consume it read
`../../util/<slice>.utils`. This is also why `@shared/util` carries no `notifications/`: those
transforms had two importers, both in `notifications/data`, so they moved home to
`notifications/util`. `@shared` keeps only what more than one domain actually shares.

`<domain>.providers.ts` declares the context via **`providePersistedContext({...})`** and exports the
resulting `<domain>Context` — a `{ providers, resolve }` bundle the domain's own route manifest
spreads (`...cashContext`) — the same file/shape whether the domain boots eagerly (composed by
`provideAppKernel()`) or per route (handed to a route's `providers`); lifecycle is a property of the
composition site, not of the bundle's name. Sheriff tags come from the two path segments
(`src/app/<domain>/<type>`), so the depth below `data/` carries no boundary — only this convention.

**Sheriff dep rules** (`pnpm exec sheriff verify`): domains sealed (`domain:* → sameTag, domain:shared`). After **sheriff-tighten** there are **no** explicit cross-domain bridges left — every domain is sealed to the default. `barcode` now owns its own `barcode` slice (the SIGIL badge), so the last bridge `barcode→office-time` is gone (§1); the old grocery bridges (`shopping↔storage`, `shopping/storage→globals`) are intra-`groceries` (`sameTag`); `notifications→tracking` and `commlink→…` are inverted behind `@shared` contracts. Type axis: `routes → feature/data/util` (a domain's own route manifest — see Routing), `feature → smart-ui/ui/data/util/model`, `smart-ui → ui/data/util/model` (**strict leaf — no `sameTag`**; a smart component composes dumb UI, never another smart component. The edit-dialog wrappers that compose store-connected sub-components therefore live in `<domain>/feature/`, and `categories-dialog` is rendered by those wrappers instead of nested inside `category-input` — §2. **`@shared` has no `smart-ui` layer** — its last inhabitant became a dumb `ui` component when the `itemDialogs` slice was retired), `ui → util/model`, `data → util/model`, `util → model`. `type:testing` may reach any layer but only `*.spec.ts` may depend on it. Each **`<domain>/data/` is a facade barrel** (`index.ts`): outside code imports the folder (`…/data`) and sees only the public facade (action group · published selectors · the `<domain>Context` bundle · any `ListPageFacade`); reducer/effects/internal selectors are encapsulated (deep import = violation). Other layers stay barrel-less (`enableBarrelLess: true` — per-folder, not global). **`@shared` is layered downward:** `@shared/data` holds only what is genuinely NgRx, itself sliced by role — `actions/` (the two published contracts `DashboardActions`/`NotificationsActions` — both write-**only**, so `@shared/data` has **no `selectors/`**: it names no domain's store key — plus `item-list.actions.factory`, the event map every list-backed context spreads), `effects/` (`persisted-slice.effects.factory` — the functional load/save/telemetry effect builders — plus `item-list.effects.factory`), plus `persisted-context.provider` (the descriptor that composes them into a context bundle), `boot-hydration.provider` + `module-hydration.resolver` (the store root is composed inline in `app.providers.ts`, not a `@shared/data` file; the eager `settings` slice moved out to its own `settings/data` domain). The `ItemDialogService` and the list engine's pure logic sit a layer down in `@shared/util` — they carry no NgRx (`item-dialog.service`, `list.utils`/`list.selector`, `LIST_FACADE`+`IListPageFacade`); a domain's own pure logic sits in its own `<domain>/util/`, never in `data/`. **The `dashboard` read-model is NOT shared** — reducer/selectors/`DashboardFacade`/persistence effects live in `commlink/data`, its types + `summary-` keyspace in `commlink/model`, its fixture in `commlink/testing` (its only readers are the deck + the shell badge); only the telemetry _port_ (`DashboardActions.report` + `IDashboardTelemetry` + `createTelemetrySliceEffect`) stayed in `@shared`, which is what keeps suppliers sealed off from `commlink`. The read-model's own `load`/`hydrate` lifecycle is a separate commlink-owned group (`DashboardReadModelActions`, same `'Dashboard'` source string) — `hydrate` carries `IDashboardSummary`, which `@shared` may not name. A domain's `data → @shared` is a downward `data → util`/`model` edge plus the contract edge; `sameTag` on `type:data` otherwise remains only for intra-slice wiring.

**There is no root-state type.** `IAppState` was deleted: every slice is read through its own `createFeatureSelector<ISliceState>('key')` and every facade injects the bare `inject(Store)`; a feature needing several slices recomposes them locally (groceries no longer has to — its aggregates are one slice, so `selectGroceriesState` _is_ the cross-list read). A complete root type is impossible by construction — the eager slices (`dashboard`, `settings`, `notifications`) are domain-owned (Sheriff bars `@shared/model` from naming a domain type), every other context is lazy, and `main.ts` may not import `type:model` at all — so the only survivor is the test kit's `TMockKernelState`/`TMockState` (`@shared/testing/test-data`), scoped to what `provideMockStore` seeds by default. Deleting it also made `@shared/model` NgRx-free, so `src/app/@shared/model/app.types.ts` is **no longer** on the eslint `@ngrx` allowlist.

### Routing (`src/app/app.routes.ts` + `<domain>/routes/<domain>.routes.ts`)

Hash routing (`withHashLocation()`). **`app.routes.ts` is a `path → loadChildren` table that names no domain internals** — every domain publishes its own route manifest at `<domain>/routes/<domain>.routes.ts`, which owns that domain's paths, titles, `<domain>Context` spread, facade bindings and `loadComponent`s. The manifest is tagged `domain:<domain>` + **`type:routes`** by the existing `src/app/<domain>/<type>` pattern, so the domain axis seals a domain's routing to its own pages + `@shared` — the shell carries no `domain:` tag and could otherwise reach anything, which is what the old flat table did. Sheriff enforces it on `loadComponent` too, because it collects imports via `ts.preProcessFile`, which reports dynamic `import()`. The manifest deliberately does **not** live in `feature/` (`type:feature` has no `sameTag` since sheriff-tighten §2/§3, so loading a sibling page from there would need that rule re-opened). The `loadChildren` edge being the only shell→domain import is also what finally keeps the eleven data layers **out of the initial chunk** (1.48 → 1.40 MB raw; ≈ 0 on the wire — ngsw prefetches `/*.js` — so the win is boot parse/eval + the seal, not KB).

**Every path is a domain prefix.** Root entries: `commlink` (home/deck), `tracking`, `data/:listId`, `office-time` (+ `/settings`), `settings`, `barcode`, `notifications`, `geist`, `soykaf` (the recipe book), `groceries/*`, `tasks/*`, `cash/*`, `trackplay/*`; `**` → `commlink`. The grocery pages live at **`groceries/{shopping,storage,products,categories}/:listId`** + `groceries/list-settings` (products was `/database`, listId `_products`), and the tasks catalog at **`tasks/categories`** (was `categories/_tasks`) beside `tasks/:listId` — so no cross-domain path ordering is left in the root table; a domain orders its own pages (`cash/rules` before `cash/:accountId`, `tasks/categories` before `tasks/:listId`). Only `/soykaf` and `/data/:listId` deliberately don't read as their folder — they are deck programs, product surfaces rather than structure. **Old pre-prefix URLs are not redirected** (`**` lands them on the deck). `commlink` has a second page, **`/commlink/deck`** — the deck configuration — which `/settings` reaches by a _link_: `settings → commlink` is a domain violation, so the page that edits the deck lives under the deck's owner rather than under the settings prefix.

A manifest spreads its context (`{providers, resolve}` = state + effects + a `moduleHydrationResolver(load, loaded)` that blocks activation until the scoped `loaded` fires) **once on a componentless subtree root** wherever the domain has more than one page there — `groceries` (5 pages: the three lists, the catalog and the flags page — one slice, so there is nothing to co-register), `cash` (6), `trackplay` (5), `tasks` (2), `office-time` (2) — so the slice registers once and `[X] load` fires **once per subtree entry instead of once per page** (Angular reuses a parent whose params don't change; measured: 2 reads per grocery page before, 0 to move between them now). Single-page mounts spread it inline: `tracking`, `data/:listId`, `barcode` (its own single-slice context since sheriff-tighten §1) and `soykaf`, which spreads the same `groceriesContext` as the `/groceries` subtree — recipes are an aggregate of that one slice, and `/soykaf` is its own mount only because it is its own program. `notifications` and the app-global `settings` page are lazy pages over **eager** slices (the inbox; the sealed `settings` domain), so they spread nothing, and `geist` spreads nothing because it has **no slice at all** (its transcript is a component signal — the session lives in the browser, not in our state). Titles via `data.title` on the leaf route + `AppTitleStrategy` (deepest wins, so nesting is transparent).

### State (NgRx)

**NgRx is sealed inside the data layer behind per-domain facades.** No `@ngrx` import lives outside `data/` — every component/shell dispatch and read goes through an `@Injectable({providedIn:'root'})` **`<Domain>Facade`** in `<domain>/data/` (the only place `Store` is injected for that domain's consumers): it exposes state as `selectSignal(...)` signals (route-parameterised reads as factory methods) and commands as `dispatch(...)` methods. Facades: `TrackingListPageFacade`/`TasksListPageFacade`/`GroceryListPageFacade` (these also implement `IListPageFacade`, wired to `LIST_FACADE`) + `ListSettingsFacade`, `TrackingFacade`, `CashFacade`, `TrackplayFacade`, `OfficeTimeFacade`, `NotificationsFacade`, `BarcodeFacade`, and the eager, domain-owned `DashboardFacade` (`commlink/data`) + `SettingsFacade` (`settings/data`). `tracking` is the one domain carrying **both** shapes — the list binding, and a `TrackingFacade` for the timer/archive/stats/CSV surfaces that are not list concerns (CR-045). **The edit dialogs hold no NgRx state at all:** the draft is a component-local `linkedSignal` and the open-command is one nullable signal on the root `ItemDialogService` (`@shared/util/item-dialog.service`, no `@ngrx` import). The store was the wrong primitive for transient, never-persisted UI state — it cost a duplicated `listId` guard in every lazy orchestrator effect (effects are never torn down), a two-hop action round-trip per open just to derive two label strings, and a per-domain selector + facade signal purely to cast `IBaseItem` back to a domain type. Every open path already started in a facade method holding its list state as a signal, so the seed item is built synchronously there and the three `*-item-dialogs.effects.ts` files are gone, guards and all. `ItemDialogService.open()` copies the item — that is what makes the wrappers' `linkedSignal` draft reseed when the same row is reopened after an aborted edit. The shared `BaseEditItemDialog` reads the command off the host + delegates save/category ops to `void` hooks the subclass wires to its domain facade. **Two dialog lifetimes → two sibling bases in `@shared/feature/`:** `BaseEditItemDialog` for the always-mounted list-item dialogs, and `BaseModalDialog` for the imperatively-presented cash/trackplay modals (the component only exists while open; `TForm` is a view-model, not the entity, since those edit mapped fields like signed-amount-as-magnitude+direction). Its `componentProps` id is a signal behind a domain-named setter, which makes `existing`/`draft` reactive and means **no dialog implements `OnInit`**. **Every dialog in the app is on Signal Forms — both families.** For the list dialogs the **base owns the field tree**: `BaseEditItemDialog` declares `form(this.draft, …)` carrying `requireUniqueName`, and the six wrappers supply only a `blank()` (the closed-state draft: a field tree cannot be built over `T | undefined`, so "closed" stays `isOpen` alone and the draft is simply never absent — the blank is never saved, since `confirm()` is only reachable from a seeded dialog) plus the `siblings` the rule compares against. Six wrappers each declaring their own `form(this.draft, rules)` meant six copies of one call and a seventh that omitted it would have _compiled_ — permanently saveable, persisting `name: '   '` for `persist()` to trim to `''`. **An invariant every subclass must hold is not a subclass's decision.** Two consequences: a generic `T` makes the mapped path type deferred, so the base narrows `path` once via `T extends IBaseItem`; and an `extraRules` hook, if one is ever needed, has to be a prototype **method** — a field would not exist yet when `form()` evaluates its schema. `blank()` delegates to the domain factory (`createRecipe('')`, `createProduct('')`, …) rather than re-listing defaults: two of the six hand-written copies had already drifted from the factory that owns them, and the deleted `blankBaseItem()` was a null object (`id: ''`) that broke `IBaseItem`'s invariants in `@shared`. **The `siblings` a name rule reads must be the whole aggregate, never a page's view of it** — four wrappers fed it `select*ListItems`/`facade.items`, which apply the list page's own search query and category filter, so a search term left in the box shrank the sibling set and a duplicate saved. Each list now publishes an aggregate read beside its page view (`selectStorageItems`/`selectProductItems`/`selectShoppingItems`, `selectTaskItems`, `selectTrackingItems`, and `selectRecipes` which was always one), and the per-list page-view selectors — vestigial once the engine went route-keyed — are deleted. That retired the app's **last reactive-forms usage**: `app-item-name-input` was a `FormControl` with its own validator, an `ngOnChanges` reseed and a `statusChanges` subscription, and the shared modal shell read validity off it through a template ref — so a _domain_ rule on the name could disable saving while a domain rule on any other field could not. The control is now a `FormValueControl<string>` that renders whatever the bound field reports (`errors` is one of the optional `FormUiControl` inputs the `Field` directive fills in), and the shell takes `[nameField]` + a **required** `[canSave]` (optional-with-`false` would turn a forgotten binding into a permanently dead Save button instead of a compile error). Its message is an `<ion-note class="sr-field-note">` of the control's own, **not** `ion-input`'s `errorText`: Ionic renders that only while the `ion-input` host carries `ion-invalid ion-touched`, and those classes come exclusively from `@ionic/angular`'s `ValueAccessor` — which needs an `NgControl` on the `ion-input` itself, so binding `[formField]` to a _custom_ control leaves the slot permanently empty. A custom control also reports `touched` only through an output literally named **`touchedChange`** (`listenToCustomControlOutput`); the name and money inputs emit it on blur. **All seven `BaseModalDialog` subclasses are on Signal Forms too** (`@angular/forms/signals`, experimental on v21 and adopted anyway — the v21→v22 export diff is purely additive): the subclass declares `protected readonly form = form(this.draft, <slice>Rules)` — which _projects_ the draft signal instead of copying it, so the base's reseed still reaches validity — and the base derives **`canSave = form().valid()`**, so no dialog re-states its schema in a hand-written conjunction. Controls bind `[formField]` through the CVA every `@ionic/angular` control ships, and the app's three custom widgets are `FormValueControl`s so they bind the same way (`app-money-input`, `cash-category-picker`, `app-date-input` — each exposing its state as a `value` **model**, because that name _is_ what `[formField]` writes through; an `input()`/`output()` pair instead makes `FormField.ɵngControlCreate` throw `NG1914`). The one field still bound imperatively is a control that drives two at once (the rule builder's field select resets the op), which stays on `patch()`. Money is never a form string: **`app-money-input`** (`cash/ui/money-input/`) is a `FormValueControl<number | null>` over integer **cents**, using `transformedValue({parse, format})` — which sets the model _before_ it writes the raw text back, so the box is never reformatted mid-keystroke, only on a reseed. Three rules are shared, all in `@shared/util/form-rules.ts`: `requireText` (whitespace-aware, because the built-in `required()` counts `'   '` as present while every `persist()` trims), `requireUniqueName` (the list dialogs' name rule, called once from `BaseEditItemDialog` — it takes `siblings`/`editing` as **thunks**, because `form()` evaluates a schema _eagerly_, before the fields they read exist) and `requireParseableDate` (a cleared date box would otherwise persist `dayjs('').format()` — the _string_ `'Invalid Date'`, which sorts above every real date and can never be reconciled). `cash/…/reconcile-modal`, `cash/…/import-preview-modal` and `trackplay/…/game-settings-popover` stay on plain `ModalController` — they are confirm/preview/popover surfaces with no entity to edit. **Enforced** by an eslint `no-restricted-imports` ban on `@ngrx/*` across `src/app/**`, re-enabled only in `app.providers.ts` (the eager-kernel composition), `**/data/**` (incl. `@shared/data/effects/**`, the generic per-context load/save/telemetry effects), the test kit, and `*.spec.ts` (`main.ts` no longer needs it — it just calls `provideAppKernel()`). Facades are root singletons — a component spec that overrides a selector between two `createComponent` calls must `store.refreshState()` (the signal is shared, not per-instance).

**Three facade file shapes, one rule: the `-page` suffix encodes a token binding, not page-ness.** `<domain>.facade.ts` is the domain's general facade (`TrackingFacade`, `CashFacade`, `TrackplayFacade`, `BarcodeFacade`, `OfficeTimeFacade`, `NotificationsFacade`, `SettingsFacade`, `DashboardFacade`); `<aggregate>-page.facade.ts` is reserved for implementations of a **shared page contract token** — `LIST_FACADE`/`CATEGORIES_FACADE` — which is what `GroceryListPageFacade`, `TasksListPageFacade`, `TrackingListPageFacade`, `GroceryCategoriesPageFacade`, `TasksCategoriesPageFacade` and `CashCategoriesPageFacade` all are; and `<aggregate>.facade.ts` is an aggregate facade inside a multi-aggregate domain that binds no token (`RecipesFacade`, `ListSettingsFacade`). Those last two back a page as well, which is exactly why `-page` has to mean the token binding and nothing else. The name's first token follows the **aggregate**, not the domain folder: `GroceryListPageFacade` matches the `grocery-list` multi-list engine, not the `groceries` domain.

The eager kernel is composed by **`provideAppKernel()`** (`src/app/app.providers.ts`, called from `main.ts`): the root `router` reducer (`provideStore`/`provideRouterStore`, composed inline here) plus three eager **domain** bundles that each register from their own `<domain>.providers.ts` — `commlinkContext`, which is `mergeContexts` of **two** slices, `dashboard` (the read-model; a sink every module writes to, badge always-on) and `deck` (see _The deck catalog_), `notifications` (`notificationsContext`; the same argument — a fan-in sink every module publishes into, plus the OS reminder `init()`) and the now-**sealed `settings` domain** (`settingsContext` — the persisted schema `version` anchor **plus the selected UI `theme`**, `TTheme`; `SettingsEffects` mirrors it onto `<html data-theme>` via `theme.service` and lifts the boot splash). Ownership (which domain owns the reducer/effects) and lifecycle (eager vs routed) are independent axes: every domain exports one context bundle from `<domain>.providers.ts`, and whether it is spread into `provideAppKernel()` or into a route is the only difference (the descriptor's `hydrate: 'boot' | 'route'` switches the boot dispatch for a route resolver) — no reducer/effect/action escapes its domain barrel either way, and settings is no longer in `@shared/data`. (`itemDialogs` is **no longer** eager — the slice is gone.) (`listSettings`/`quickadd` are **no longer** eager — they were grocery-specific all along and moved into the lazy `groceries` domain in the settings re-scope; the one app-wide thing they carried, the `version`, became the global `settings` slice.) **Every bounded context except the notification inbox is lazy:** `tracking`, `groceries`, `tasks`, `cash`, `trackplay`, `barcode`, and `officeTime` register per-route via their `<domain>Context` bundle (`<domain>/data/<domain>.providers.ts`) and hydrate in that bundle's `moduleHydrationResolver`, not eager. `groceries` is **one slice** (`state.groceries` = products · shopping · storage · recipes · listSettings, one `npc-groceries` doc, one `[Groceries] load/loaded`), so every grocery route — the lists, the catalog, `/groceries/list-settings` and `/soykaf` — spreads the same bundle; the ephemeral `quickadd` reducer rides along, merged in without a lifecycle because it is never persisted. No global load action — each context owns a scoped `[X] load/loaded` lifecycle and its reducer hydrates on its own `loaded`; each eager domain boots its own hydration via `hydrate: 'boot'` (a `bootHydrationProvider(...)`) inside its own bundle (settings dispatches `SettingsActions.load`, dashboard its read-model load; the theme rides in `settings`) — `main.ts` itself only calls `provideAppKernel()`.

**The deck catalog — one user-configurable list behind the grid AND the side menu.** `DECK_CATALOG` (`commlink/model/deck.catalog.ts`) is every navigable destination — the 13 deck programs plus the two menu-only rows (the deck's own home link, `groceries/list-settings`) — and `CommlinkPage` and `app.component.html` both render from it via `DeckFacade`, neither holding a list of its own. It is **commlink's** because a domain owns the routes it _serves_, not its own presentation in navigation (`groceries` has no opinion about being MARKET, seventh, with a cart icon); per-domain entry manifests would also have forced the shell to import all eleven domains eagerly, undoing the `loadChildren`-only seal. It costs no new coupling either — the shell already imported exactly one domain (`DashboardFacade`). The catalog carries **no single label**: codenames are theme-scoped, so each entry declares a `labels: Record<TTheme, {nameKey, descKey}>` of `marker(...)` literals that `resolveLabels` indexes by `ThemeService.theme` — spelled out rather than composed, because a composed key is invisible to `i18n:extract --clean`, and typed as a `Record<TTheme, …>` so a new theme is a **compile error at all 15 entries** instead of a raw key on screen. **Both** surfaces render the resolved `nameKey`, so a menu row and its tile can never disagree; `titleKey` (`page-title.*`) stays the _page's_ title, for the toolbar and `AppTitleStrategy`. Splitting them is also what stops the menu listing "Einstellungen" twice — `/settings` and `/groceries/list-settings` share a page title but have distinct names. `hex` is no longer a field — it is the tile's _slot address_, `$index | hex`, so the top tile always reads `0x01`. The persisted config (`npc-deck`, eager) is three id lists — `order` · `hiddenEntries` · `hiddenModules` — where **absence means default**: a new catalog entry appends and renders, a retired id is ignored on read, so the catalog grows and shrinks with **no migration hop** (only _renaming_ an id would need one, so ids are never renamed). `order` is a list rather than an `order: number` per entry because a list IS the order (no renumbering per drop, no gaps, no two entries claiming 3), and a module's flag **cascades at read time and is never written into its entries** — re-enabling a module restores what the user configured underneath instead of flattening it. `SYSOP` is hideable like everything else, which is why the menu toolbar carries a **permanent settings icon button**: without it a user could hide the only door back to the page that un-hides it. Rationale in `docs/project-summary.md` §7.1.

**tracking ↔ notifications — how the cross-cutting couplings were resolved:** the background `runningUpdates$` timer was **deleted** (a notification is a point-in-time event, not a live dashboard); the notification CTA **deep-links** (`/notifications` → `/tracking?cmd=<command>&target=<itemId>`, a string route carrying the command the inbox already holds — notifications imports no domain, and the producer resolves the command against its own items instead of looking the row up); tracking **publishes** into the inbox by dispatching the shared `NotificationsActions` and **never reads it** — `project` hands over the complete row set it owns (derived from its items alone) and the reducer merges: rows other owners published are untouched, ones tracking stopped projecting are dropped, and an unchanged `origin.variant` keeps a row's `updatedAt` so a cascade can't drag it to the top. That is what let the shared read half (`@shared/data/selectors`, the kernel naming another domain's store key) be **deleted**; the cost is one idempotent write per tracking mutation instead of a delta computed against foreign state. The always-on notification **badge** still reads the `dashboard` read-model (`selectNotificationsUnread`), not the inbox slice, which keeps the shell domain-blind and gives a cold launch its persisted count.

**There is no toast service.** The published contract's fourth event, `NotificationsActions.toast({ key, params?, color? })`, carries a _transient_ message: no reducer reacts, nothing is persisted, and the notifications domain presents it in the one `NotificationsToastEffects` (the only place `ToastController` + the message's `TranslateService.instant` live; it rides `notificationsContext` because a toast can be raised on the eager boot path). Producers therefore describe the message as **data** and stay ignorant of Ionic and of i18n: tracking's five add/update/remove/save reactions became plain dispatching effects, commlink's storage-unavailable fallback emits it next to `hydrate([])`, and the two component-side cases (barcode upload failure, cash "apply rules" result) go through their own domain facade (`reportUploadFailure()`/`reportRulesApplied(count)`) — a component may not dispatch. Trackplay's undo toast is deliberately **not** on this contract: it is an interactive affordance (a button that dispatches `restore`, superseding the previous toast), not a message, so it keeps its own `ToastController` in `trackplay/data`.

**Why the inbox is eager (and `tracking` is not).** `feature/fully-lazy` routed _every_ context, notifications included. That forced a second write path — producers had to read-modify-write the persisted `npc-notifications` doc through a `NotificationsStore` port, sharing the reducer's pure transforms so the two paths could not drift — plus a re-hydrate on route entry to correct a slice that could be stale. The port is now **deleted**: a fan-in sink written from every route and read by always-on shell chrome has no route to be scoped to, so it boots in the kernel like the dashboard read-model, and producers just dispatch. `/notifications` is still a lazy _page_ (`loadComponent`) — page laziness and slice lifecycle are independent. The lesson: **route a context by its writers, not by its page.**

> **⚠️ lazy ≠ unloaded on exit.** `IonicRouteStrategy` has no `shouldDestroyInjector` and NgRx `provideEffects`/`provideState` have no per-injector teardown, so a lazy route's injector + effects + state register on **first visit and persist for the session** — modules are **not** mutually exclusive. Two lazy modules that subscribe to the **same** action BOTH fire once both are visited (NgRx dedups same-class instances, never different classes) — so each such effect must **guard on the target `listId`** (grocery ∈ `{_storage,_products,_shopping}`, tasks `=== '_tasks'`), reading the same field it routes on. This guard tax is what motivated moving the dialog open-command off the action bus: the three orchestrators existed largely to carry it, and calling `ItemDialogService` directly from each domain facade makes cross-firing structurally impossible. "Lazy" here is a boot-cost win, not memory reclaim.

- **Action-group event keys are camelCase identifiers, not quoted title-case strings** — `addItem:`, never `'Add Item':`. `createActionGroup` camelCases the key to build the creator either way, so the creator names (and every call site) are identical; what changes is the generated `type`, now `[Source] addItem` instead of `[Source] Add Item`. The point is that the wire string and the code you write are the same token, so an action is greppable by the one name it has. **Nothing may match on that string.** Use the creator (`ofType(Actions.addItem)`, `case Actions.addProduct.type:`) — the three hardcoded `case '[Storage] Add Product'` literals in `grocery-list.effects` were the only things the rename broke, which is exactly why they now read `.type` off the creator. Parsing the _source_ prefix is still fair game (`listIdByPrefix` reads `[Storage]`), since that is a slice identity rather than an event name.
- **One multi-list engine + shared single-list helpers.** `groceries`' `grocery-list.*` files (actions/selectors/effects, each in its `data/` role folder, plus the pure `grocery-list.utils` in `groceries/util/`) are the multi-list engine (source `[GroceryList]`) — `selectListState` derives the active list from the `:listId` route param via `router.selector` + `stateByListId`. The single-list domains (`tracking`, `tasks`) have **no** separate engine: each owns its slice (`state.tracking`/`state.tasks`) and builds its list flow (add-from-search, sort, search-sync) on the domain-blind `@shared/util/list` helpers (`list.utils`/`list.selector`), driving the shared `ListPageComponent` via its own `*ListPageFacade`. Tracking's former standalone item-list engine (`[ItemList]` shim) + `dialogs` slice were retired onto these shared mechanics + the shared `ItemDialogService` open-command (the last timetracker×kitchen-bot merge-duplicate).
- **Recipe book (SOYKAF) — a fourth grocery aggregate** (`a8c9a74`). `recipes` is a slice of `groceries`, not a domain of its own: a recipe is expressed in the grocery vocabulary (its ingredient lines _reference_ `_products` catalog ids, "do I have it" _is_ `_storage`), so the matcher reads its siblings via `sameTag` instead of needing a re-opened Sheriff bridge. **Both halves of the match are id-based.** The recipe half always was (an ingredient references a product); the storage half became so when `IStorageItem`/`IShoppingItem` gained an optional `productId` (`TProductLinked`) that the copy factories stamp and carry across every hop — product→storage, product→shopping→storage (the common one: buy, then move the bought rows), storage→shopping. Before it, the storage side resolved `productId → product.name → a row with that name`, so renaming a product silently broke "do I have it" until the row was renamed too. The name comparison **stays as a fallback** rather than being retired: the field is optional, and it is legitimately absent two ways — a row typed straight into the pantry was never a product, and rows persisted before it have none, which is what keeps the fix migration-free. In the tree: `actions/recipes.actions.ts` · `reducer/recipes.reducer.ts` · `selectors/recipes.selector.ts` · `recipes.facade.ts` (+ the pure matcher one layer down in `groceries/util/recipe-match.utils.ts`), telemetry `source: 'recipes'` + `createMetric('count')` (which flipped the SOYKAF tile standby→online). It has **no context file of its own**: recipes are one of the five aggregates _inside_ the `groceries` slice, so they hydrate on `[Groceries] loaded` with their siblings and persist in the same doc — the matcher joins them against products + storage, and being one slice is what makes reading a sibling structurally safe rather than a co-registration rule. The page is `groceries/feature/recipes-page` (+ `edit-recipe-dialog`), loaded by the unchanged `/soykaf` path — **route path ≠ folder**, and the `kitchen` domain is deleted. It deliberately does **not** ride the shared `ListPageComponent`: its rows carry a match verdict, not a name and a swipe. The `/soykaf` route resolves all of them — `mergeContexts` keys each resolver by its slice key, so the merged map cannot collide. `IProduct.alwaysOnHand` (optional, so no migration) is what keeps staples out of the missing count. Decisions + deferred v2 in `docs/project-summary.md` §12.
- **Grocery slice renames vs kitchen-bot** (to avoid timetracker collisions): store keys `settings→listSettings`, `dialogs→itemDialogs`; action sources `[Settings]→[ListSettings]`, `[Dialogs]→[ItemDialogs]`, `[ItemList]→[GroceryList]`; types `ISettings→IListSettings`, `IEditItemState→IItemDialogState`, `TDialogsState→TItemDialogsState`. **Settings re-scope:** `listSettings`, `quickadd`, and the quick-add row (`ItemListQuickaddComponent`) now live in the `groceries` domain (they were grocery-specific, not shared); the freed bare `settings`/`[Settings]` names (typed `ISettingsState`, like every other slice) are now the app-global version+theme slice, sealed into its own `settings/data` domain, and timetracker's own settings type/slice/source were renamed `IOfficeTimeSettingsState`/`officeTimeSettings`/`[OfficeTimeSettings]` (later removed entirely — the re-scope left it holding only a dead `showTotalTime` flag, so the whole slice was deleted as dead code). `tasks` dropped its vestigial quick-add entirely.
- **List/dialog orchestrators are per-domain + lazy** (§2b). The old eager shell `grocery-list.effects.ts`/`item-dialogs.effects.ts`/`app.effects.ts` are **deleted**. The grocery multi-list engine lives in `groceries/data/effects/grocery-list.effects.ts` (in `groceriesContext`, scoped to the three grocery lists); `tasks` **and `tracking`** each have their **own switch-free copies** (`tasks/data/effects/tasks-list.effects.ts`; `tracking/data/effects/tracking-list.effects.ts` — both `@shared`-only → sealed; tracking's guard on `listId === '_tracking'`, tasks' on `=== '_tasks'`). The dialog orchestrators are gone entirely — the open-command is a signal service now. Each context's list-flow effects ride in its own bundle's `effects: [...]`, while save + load + telemetry are declared on the descriptor; the inbox's remaining own effects (debug + toast) ride in `notificationsContext` the same way.

### Persistence (`src/app/@shared/util/db/database.service.ts`)

`@ionic/storage-angular`, DB name `np-commlink`, keys namespaced `npc-<slice>` (+ `npc-summary-<source>` for the persisted dashboard read-model). It is a **dumb per-key port**, domain-blind by construction: `bootstrap()` only initializes (init-once guard + schema-version check, no read); each context reads/writes its own key via `load<T>(key)` / `save<K>(key, value)`, or a whole key _family_ via `loadPrefixed<T>(prefix)` — commlink's `summary-<source>` docs are the only family, and commlink owns that prefix (`commlink/model`). All four await the init-once guard. Versioning is app-level (`APP_VERSION`, `@shared/model/app.consts`), migration is per-context: every doc is stamped into a `{v,data}` envelope on save and migrated on read by `runMigrations` (`@shared/util/db/versioned.ts`). A context supplies a `ladder` to `providePersistedContext` **only when it has a hop to declare** — the ten always-empty `*.migrations.ts` files are gone and the descriptor defaults it to `[]`. The schema `version` now lives in exactly one place: the eager app-global `settings` slice (`npc-settings`), seeded on first boot by `SettingsEffects` (the per-slice `version`s on `listSettings` + office-time were dropped in the settings re-scope). `quickadd` is ephemeral and **not** persisted (and grocery-owned now); the dialogs hold no store state. `npc-deck` needs no ladder by construction — it stores only entry _ids_, and an unknown one is ignored on read while a missing one takes its default (see _The deck catalog_). Fresh-install only — no migration from the old `np-time-tracker` / kitchen-bot databases.

**No cross-module write port.** `npc-notifications` is written by exactly one thing: the inbox's own `NotificationsSaveEffects`, on every write including a producer's — so a producer dispatches and stays ignorant that notifications are persisted at all (the same arrangement as the dashboard read-model). The `NotificationsStore` read-modify-write port this used to need is deleted; see _Why the inbox is eager_ under State.

### i18n

`@ngx-translate/core` **v18** — provider API only: the root is `provideTranslateService({lang, fallbackLang, loader: provideTranslateHttpLoader({prefix, suffix})})` in `main.ts`, and **`TranslateModule` no longer exists**, so a component imports the standalone **`TranslatePipe`** and a spec off the shared kit calls `provideTranslateService()` (`BASE_TEST_PROVIDERS` does it for the rest). Importing the pipe instead of a module is also what makes an unused i18n import visible: the compiler reports `NG8113` on a pipe it cannot find in the template, which a module import always hid. **Bilingual, German default.** The UI language is a `language` on the eager `settings` slice, applied by `SettingsEffects.applyLanguage$` through **`LanguageService`** (`@shared/util`, the exact sibling of `ThemeService` and for the same reason — `commlink`/`cash`/`trackplay` read the locale and may not import `settings`), which owns the three globals a language touches: the translate bundle, `dayjs.locale`, `<html lang>`. **Switching restarts the app** (`restartOnLanguageChange$`): money/score/date render through _pure_ pipes whose output is cached on input identity, and `LOCALE_ID` is a provider that cannot be re-resolved — so a live switch would leave the screen half-formatted. The restart awaits `DatabaseService.settled()` so it cannot overtake the descriptor's save effect and drop the choice. `LOCALE_ID` + the first bundle come from a synchronous `localStorage` mirror (`bootLanguage()`), because a provider cannot await IndexedDB; the settings doc stays the source of truth and the restart is what keeps them from ever being observed apart. **Money parsing takes the language explicitly** — `12,34` read as English is a valid grouped amount (1234 €), so the conventions are mutually ambiguous and nothing can be rejected: bank CSV parsers pass `'de'`, and a persisted rule threshold is _normalized_ onto German on save so a switch cannot re-interpret existing rules. **Every display format is locale-named, never a German literal**: `date:'short'`/`'shortTime'`/`'fullDate'` in templates, and `localizedDate`/`localizedLongDate` (`@shared/util/date-format.utils`) for the dayjs call sites. That module owns dayjs's plugin _and_ its locale packs because both fail silently — `format('L')` without `localizedFormat` returns the literal `"L"`, and `dayjs.locale('de')` without the pack keeps the previous locale — so importing it is what makes either impossible. Flat dotted keys. **All kitchen-bot keys are namespaced under `grocery.`** (`public/i18n/{de,en}.json`) to avoid collisions with timetracker keys. TS keys not used via the `translate` pipe must be `marker('grocery.…')`.

**Page titles are the one namespace keyed by page, not by domain: `page-title.<domain>[-<page>]`** — `page-title.cash`, `page-title.cash-rules`, `page-title.groceries-shopping`, `page-title.trackplay-games`, `page-title.office-time-settings`, `page-title.categories`. A title is read by the shell (`AppTitleStrategy`, the side menu) as much as by its page, so it lives in one flat namespace rather than under five different domain prefixes — which is also what retired `officetime.` (≠ the `office-time` domain), the `cash.`/`trackplay.` title prefixes, and tasks' title hiding under `grocery.`.

### Types

**Sliced by concern, never a god file — and never a barrel: `<domain>/model/<concern>.types.ts` everywhere.** Every model layer now reads the same way: `cash` splits into `account`/`transaction`/`rule`/`cash.types`, `groceries` into `grocery-list`/`recipe`/`list-settings`/`groceries.types`, and a domain whose model is one tightly-coupled concern keeps one file named for it (`barcode.types`, `tracking.types`, `task.types`, `trackplay.types`, `office-time.types`, commlink's `dashboard.types`). The `model/index.ts` barrels are gone, so an import line names the vocabulary it uses instead of the folder; a `*.consts.ts` appears only where there is a body of constants (`geist`), not for a domain's one list-id.

In `@shared/model`, `app.types.ts` keeps only the primitives every layer speaks (`TMarker`/`TTimestamp`/`TColor`/`TTheme`/`TIonDragEvent`); each shared concept owns a file next to it — `base-item.types` (`IBaseItem`/`TUpdateDTO`/`TEditItemMode`), `category.types`, `item-list.types`, `notifications.types` (the inbox shapes **plus** the `IToastMessage` contract), `dashboard.types`, `settings.types`. The layer is **barrel-less** (Sheriff `enableBarrelLess`), so import the concern's file directly — which is what makes an import line say which shared vocabulary a file actually depends on. `IItemList<T>` requires `categories`/`mode` (grocery reads them unguarded; the tracking list carries empty defaults). There is no shared datastore type: `DatabaseService` is generic over the caller's `T` (see Persistence).

### Capacitor / Android / two barcodes

`appId np.afterwork.commlink`, `webDir www/browser`. Plugins: the timetracker set + `@capacitor-mlkit/barcode-scanning`. **Two unrelated "barcode" features:** `barcode/` (SIGIL — displays an uploaded badge image, no camera) and `groceries/util/barcode-scanner.service.ts` (mlkit EAN-13 camera scanner, wired to a native-guarded scan button on the shopping/storage pages → feeds `GroceryListPageFacade.showCreateProductFromScan`, which is also why it lives in `groceries`, not `@shared`). The `android/` folder is **git-ignored and regenerated on demand** (not committed): `npx cap add android` once per machine, then `pnpm run build:android` (= web build → `cap sync android` → `./scripts/android-postsync.sh`) for every rebuild. The postsync step re-applies the edits Capacitor strips on every sync — the mlkit `barcode_ui` `meta-data` + `CAMERA`/`FLASHLIGHT`/`POST_NOTIFICATIONS` permissions, and `versionName 1.0.0`/`versionCode 1`. The script is idempotent. The generated activity `configChanges` is already the rich Capacitor-8 set, so it needs no augmentation.

**GEIST is web-desktop-only, by design.** `@shared/util/language-model.service.ts` wraps **Chrome's built-in Prompt API** (Gemini Nano, on-device — no key, no network per prompt), which exists in desktop Chrome 148+ and **not** in Chrome for Android, iOS, or the Android System WebView Capacitor renders into. So `unavailable` is a permanent, expected outcome on the APK target, not an error: the page renders its NO RESONANCE explainer instead of a dead prompt, and the deck tile goes dark. **There is deliberately no synchronous `isSupported`** — the `LanguageModel` global is exposed on _any_ secure http(s) origin, including browsers with no model behind it (headless Chromium reports `downloadable`), so its presence says nothing about whether a prompt can be answered. The service therefore probes `availability()` **once**, memoized, and publishes it as a signal both readers share: the page drives its own link state machine off it, and `CommlinkPage` maps it through `LANGUAGE_MODEL_STATUS` (`available` → online · `downloadable`/`downloading`/`probing` → standby · `unavailable` → **offline**), which is why `onlineCount` had to become a `computed` — a capability resolves after first paint. Build wiring is easy to miss — the ambient globals come from the `@types/dom-chromium-ai` devDependency, which must be listed explicitly in `tsconfig.{app,spec}.json` `types` (this project opts out of auto-inclusion), plus `DOM.AsyncIterable` in the root `lib` for `promptStreaming`. Streamed answers render in a `<pre>`: the model's newlines are meaningful and `<pre>` is the one element whose whitespace Prettier will not reflow. No e2e — the happy path is unreachable from headless Chromium and the module is an experiment.

## Theming — two themes (Cyberpunk deck + OK Boomer)

**Two** themes off one token group: **cyberpunk** — the Shadowrun deck (near-black slate, amber + teal neon, monospace, glow, HUD frame; the **default**) — and **OK Boomer** — a plain, light, serious office look (sans-serif, flat surfaces, sentence case, no neon). **Do not restyle components one by one** — retheme the CSS custom properties. The active theme is the **`<html data-theme>`** attribute (default `cyberpunk`), driven by the eager `settings` slice (`selectTheme` · `SettingsActions.setTheme` · picker on `/settings`) and applied by `SettingsEffects.applyTheme$` via `@shared/util/theme.service` (also sets `<meta theme-color>` + native status-bar style). The async boot read is covered by a boot **splash** (`@shared/util/splash.service` + `index.html #app-splash` on web / `@capacitor/splash-screen` `launchAutoHide:false` on native) revealed once the theme is applied — so the theme resolves before first paint, no flash. Plan/rationale: `docs/project-summary.md` §8.

- **Plain = base, cyberpunk = opt-in.** `src/theme/_shadowrun.scss` owns the `--sr-*` palette + `src/theme/variables.scss` the Ionic `--ion-*` chrome; the **base `:root` holds the plain OK-Boomer values**, and the amber/teal-on-slate deck values live under **`:root[data-theme='cyberpunk']`** (so a new surface reads plain unless it opts in — "serious looks serious" by construction). **"Flip" tokens** turn structural axes into per-theme values so components reference a token, never a literal: `--sr-deck-font` (sans↔mono), `--sr-heading`/`label`/`brand-transform` + `-tracking` (case + spacing), `--sr-radius`, `--sr-glow`/`-lg` (→ `none` in plain). Component SCSS must use these tokens (not hardcoded `uppercase`/`letter-spacing`/`--sr-mono`); purely-decorative effects (glitch, grid overlay, scanlines, LED glow, hud gradient/bevel) are gated under `:root[data-theme='cyberpunk']` / `:host-context([data-theme='cyberpunk'])`. Every surface is uniform amber (`primary`) / teal (`secondary`); `TColor` (`@shared/types.ts`) is Ionic's base palette. `@use`d once from `src/global.scss` (which also carries the Android safe-area map + `body.scanner-active` transparency).
- Deck signature pieces are **theme-aware Sass mixins** in the side-effect-free `src/theme/_deck.scss`: `panel-base` (flat) vs `panel-cyber` (gradient+bevel), `led-base` (solid dot) vs `led-glow` (bloom+pulse), `hud-corners`, `brand`; `_shadowrun.scss` wraps them as the global `.sr-panel`/`.sr-corners`/`.sr-led*`/`.sr-brand*` classes (base emitted always, cyber variant under the deck selector). Consume via `var(--sr-*)` / the `.sr-*` classes, or `@use 'theme/deck'` + `@include` where a class can't reach (`:host`/pseudo-elements); **never `@use 'theme/shadowrun'` from a component** (it emits global CSS).
- `/commlink` deck is the reference cyberpunk expression; `/soykaf`, `/geist`, `/trackplay`, and the grocery/office-time pages all read the same shared classes. The programs render as HUD tiles from the **user-configurable catalog** (below) rather than a hardcoded array, so the grid's tile count is whatever that user shows — the status strip still reports the grid's full complement (`DECK_SLOT_COUNT`, 13), because hiding a program is a navigation choice, not an uninstall. SOYKAF is `online` now that the recipe book replaced its stub, so **GEIST is the only capability-gated one**: `CommlinkPage.status(p)` reports a `needsLanguageModel` program's _capability_ status instead of its declared one (`standby` while the weights still need downloading, `offline` where the on-device model can never exist), keeping it out of the loaded count either way, so the deck never advertises a program that cannot run there.
- **Adding a third theme** = add plain-relative values on the base `:root`, a `:root[data-theme='<name>']` override block (Ionic `--ion-color-*` + `--sr-*` + flip tokens), a `TTheme` union member (the picker renders from `THEMES` + `THEME_LABEL_KEYS`, so both must grow — they are `Record<TTheme,…>`, hence a compile error until they do), **and two full key blocks — a `labels` entry per catalog entry _and_ a `DECK_CHROME_LABELS` block for all 19 HUD slots — declared in code as well as filled in both message bundles.** Both are `Record<TTheme,…>`, so the code half **fails to compile** until it is complete, and `deck.catalog.spec.ts` then catches a key the bundles are missing (`translate` renders the raw key on a miss). The chrome block is where a theme's **voice** lives: a field names a HUD slot, not a word, so OK Boomer fills "noise" with `Ungelesen` where cyberpunk fills it with `Rauschen`. `theme/palettes/_example.scss` is the older `.ion-palette-<name>` seam reference (superseded by `data-theme`) — do **not** import Ionic's prebuilt `dark.class.css`.
- **Re-skin audit — done.** The grocery/cash dialog clipping (shared form inputs on `labelPlacement="stacked"`), the chart palettes (tokenised via `@shared/util/charts/chart-colors` reading the live theme tokens; `_charts.scss` on `--ion-color-*`/`--sr-*`), and the last hardcoded German button labels (moved to i18n) are all resolved. `docs/project-summary.md` §12 carries anything still genuinely open.

## Deployment

PWA build (`pnpm run build` → `www/browser`; manifest identity `CommLink`/`CL`, `theme_color`/`background_color` `#0f141b`) + Android APK (`pnpm run apk:debug`, or Android Studio via `pnpm run open:android`; `android/` is git-ignored — see Capacitor section). **Release APKs are unsigned** — no `signingConfig` is wired, so `apk:release` yields `app-release-unsigned.apk`; store publishing needs a keystore (a secret, hence a decision, not a default). PWA icons are still the timetracker placeholders (shadowrun icon redesign deferred). **Nothing has been pushed yet** — the remote holds zero refs, so CI has never run; web and APK ship together, so the first push waits on the keystore.

**The version lives in `package.json` and nowhere else.** The web app reads `APP_RELEASE` (`@shared/model/app.consts`) = the `NPC_RELEASE` that esbuild's `define` injects from `npm_package_version` on `build`/`build:pages` (ambient decl in `src/app-release.d.ts`; both tsconfigs already glob `src/**/*.d.ts`). The read is **`typeof`-guarded** because `ng serve` and Vitest apply no define — the identifier is undeclared there and a bare reference throws, so dev reads `dev`, which also keeps the fallback exercised. `android-postsync.sh` derives `versionName` verbatim and `versionCode` as `major*10000 + minor*100 + patch` (**minor/patch must stay < 100**): `versionCode` is the only field Android compares to allow an upgrade, and a non-increasing one forces an uninstall, which wipes the IndexedDB. This is *not* `APP_VERSION`, the persisted-schema number `runMigrations` reads — different cadences, deliberately uncoupled. A checked-in const + CI drift gate was rejected: injection has nothing to drift.

**CI/CD is Codeberg's Forgejo Actions** (`.forgejo/workflows/ci.yml` — the GitHub workflow is deleted, and `.github/` with it). It is deliberately **one job**: Codeberg's hosted runners are donated capacity whose terms ask for minimal pipelines, so every gate (eslint · prettier · sheriff · `tsc` ×2 · vitest coverage · playwright · prod build) shares one container and one `pnpm install`, and the deploy then sits behind e2e for free instead of needing an artifact hand-off. `runs-on: codeberg-medium-lazy` — the `-lazy` suffix buys a 24 h runtime budget in exchange for a delayed pickup (plain `codeberg-medium` caps a job at 10 min), and `medium` is the smallest tier an Angular build fits: Codeberg counts **filesystem writes against the RAM quota**, so `node_modules` + a Chromium download is most of a gigabyte before the compiler starts. Every `uses:` is a **fully-qualified URL** (`https://code.forgejo.org/actions/…`) because a bare `owner/repo` resolves against the instance's `DEFAULT_ACTIONS_URL`, which is not github.com here; contexts are the Forgejo-native `forge.*`. No `concurrency:` block — Forgejo defaults `cancel-in-progress` to true for push/PR.

**Verification runs on every push; publishing is release-gated on a `vMAJOR.MINOR.PATCH` tag.** A push to main runs all eight gates and deploys nothing; pushing e.g. `v1.0.0` runs the same job again on that ref and _then_ deploys — so Pages always serves a tree the run itself verified, instead of one trusted to have been green earlier. Two consequences shape the file: `on.push` carries **no filter at all**, because Forgejo rejects `branches:` and `tags:` on the same trigger (the filter moved into the job's `if:` — pull requests, `refs/heads/main`, `refs/tags/v*` — where a skipped run claims no runner); and the exact semver shape is asserted by a **`grep -Eq` in the deploy step**, not by an `on.push.tags` glob, because a glob dialect that doesn't support what was written fails _silently_ — it just stops matching and releases quietly stop happening. Pre-release tags (`v1.0.0-rc.1`) therefore verify without publishing.

**The PWA ships to Codeberg Pages, branch variant:** `https://letothec0dem0nkey.codeberg.page/np-commlink/` is the tip of _this repo's_ `pages` branch, force-pushed as a fresh orphan commit per deploy (a publishing surface, not history — keeping the commits would grow the repo by one full build per push). One site **per project**; the alternative — a repository literally named `pages` — serves a single site at the domain root, which is why the branch is the variant here. Two things live in the repo settings rather than in git: Actions must be enabled under _Units_, and a **Forgejo webhook** targeting the Pages URL with branch filter `pages` is what tells the git-pages server a deploy happened. The deploy authenticates with the automatic `forge.token` (write-scoped on push events), so there is no PAT secret.

**The subpath is why there are two prod builds.** `pnpm run build` keeps `--base-href ./` for Capacitor (loaded from `https://localhost/`); `pnpm run build:pages` sets `--base-href /np-commlink/`, because a relative base href resolves wrong the moment someone lands on the URL without its trailing slash. Serving from a subdirectory also means **no absolute in-app URL may point at the server root** — the two that did are fixed and are the pattern to follow: the `TranslateHttpLoader` prefix is `'./i18n/'` (an absolute `/i18n/` 404s and every label degrades to its raw key) and `index.html`'s favicon `href` is relative. Hash routing (`withHashLocation()`) is what spares us an SPA-fallback `_redirects` file: every route is `/#/…`, so `index.html` is the only document Pages ever has to serve.

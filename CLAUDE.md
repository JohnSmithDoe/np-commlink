# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`np-commlink` — Ionic 8 + Angular 21 (standalone, zoneless) + Capacitor 8 app. It is the **merge of two apps**: `np-timetracker` (time/office tracking, the structural + visual base) and `np-kitchen-bot` (shopping / storage / tasks / globals grocery lists, grafted in as independent features). One Shadowrun/cyberdeck look throughout. Ships as a web app (PWA) and an Android APK.

The current architecture (who talks to whom, and why) lives in **`docs/architecture.md`** — read it before touching the grocery subsystem. The merge decision log and refactor history are in the git commit log; open/deferred work is in `docs/open-tasks.md`.

> We work trunk based. so only on the main branch. if you must use a worktree instead of a branch but try to just keep up with other changes and work on the main.


## Commands

- `pnpm start` — dev server (`ng serve`). `pnpm run build` — prod web build (`www/browser`).
- `pnpm test` — Vitest via `@angular/build:unit-test` (one-shot). `pnpm run e2e` — Playwright (`e2e/`, port 4321).
- `pnpm exec eslint "src/**/*.ts"` — lint (flat `eslint.config.js`: angular-eslint + @ngrx + Sheriff + prettier).
- `pnpm run i18n:extract` — extract `marker(...)` keys into `public/i18n/de.json`.
- `pnpm run build:android` — prod web build + `cap sync android` + the postsync patches.
  `pnpm run apk:debug` / `apk:release` chain a Gradle `assemble` onto it; `pnpm run open:android`
  opens Android Studio. `sync:android` is the sync half alone (skip the Angular rebuild).

> **Testing philosophy** (inherited from timetracker). Lean, not exhaustive. Two layers:
> - **Vitest unit — pure logic** (`*.spec.ts`): utils, pipes, reducers, selectors (via `.projector(...)`). No `TestBed` where a plain call suffices.
> - **Vitest unit — component class logic** (`*.component.spec.ts`): `TestBed.createComponent(...).componentInstance` + `provideMockStore()` + `provideZonelessChangeDetection()`. **Do not `detectChanges()`** — jsdom doesn't run Stencil, so `ion-*` are inert; rendered-DOM assertions belong in e2e.
> - **Playwright e2e**: real-browser behavior. Scope content assertions with `#main-content` (the side menu duplicates page titles) and use **hash routing** URLs (`/#/groceries/storage/_storage`).
>   Four Ionic locator traps cost a red spec every time they are rediscovered — a spec that ignores them passes alone and fails after an SPA navigation:
>   - **Scope controls to the page component** — every page's selector is `app-page-<x>` (`app-page-recipes`, `app-page-storage`, `app-page-trackplay-games`), not just `#main-content`: the router outlet keeps previously-visited routes mounted (the `lazy ≠ unloaded` rule, seen from the DOM), so a sibling page's identical "Hinzufügen" button is still there.
>   - **An `<ion-modal>`/overlay teleports to the app root**, so it is *outside* that page scope — key a presented dialog off its title (or `role`), never off its wrapper element.
>   - **Click an `ion-select` host**, not its accessible button: the shadow `part="inner"` swallows the click.
>   - **Re-entering a route mounts the page a *second* time** — the same `app-page-<x>` then matches twice and every row locator inside it is a strict-mode violation (`:visible` does *not* help; the stale instance is not `display:none` at assert time). A spec that bounces between two routes should navigate with `goto` **+ `reload()`**, which collapses the outlet to one instance and makes every assertion a cold read of persisted state besides (`e2e/commlink/deck-config.e2e.ts`).
>
> Shared test infra is at `src/app/@shared/testing/` (`test-data.ts` deterministic factories, `test-providers.ts`), reachable only from `*.spec.ts` (Sheriff `type:testing`). NgRx **effects stay RxJS**. Rely on Vitest `globals:true` — do **not** `import … from 'vitest'`.

## Code style — speaking code instead of comments

We use **speaking code instead of comments**. Only ever comment the **why** — never the **how**; the how must be cleanly readable from the code itself. Prefer **small functions with human-readable names**, written as prototype functions (**skeleton → execution**): the top-level function reads as the list of steps, each step a named call that a reader can descend into only if they care. If you feel the urge to write a comment explaining what a block does, extract that block into a well-named function instead. Keep comments to an absolute minimum — the only ones that earn their place are non-derivable rationale (a domain rule, a workaround for external behaviour, a trade-off someone would otherwise "fix").

## Architecture

> **⚠️ Re-domained (2026-07, branch `feature/ddd-refactor`).** The grocery subsystem was
> restructured by a DDD refactor: `shopping`/`storage`/`products` (was `globals`) are now
> features of a **single `groceries` domain** (`src/app/groceries/`); `tasks` is its own domain,
> sealed off the grocery engine via a `ListPageFacade` (`@shared/util/list/`); the shared page
> is the domain-blind `list-page` (was `grocery-list-page`); `notifications` and `commlink` no
> longer import any domain (inverted behind `@shared` `notify`/`dashboardTelemetry` contracts);
> and the grocery cluster + `tasks` are **lazy** (co-hydrated via a route resolver). Some
> descriptions below predate this — **`docs/architecture.md` is the current, authoritative
> structure.**

Standalone app bootstrapped from `src/main.ts` (no `AppModule`). All providers (router, store, effects, Ionic, translate, storage) are wired in `bootstrapApplication(...)`.

### Folder layout (Hahnekamp-style, Sheriff-enforced)

Domain-first, sliced by type; every dir carries a `domain:*` + `type:*` tag (`sheriff.config.ts`).

```text
src/app/
  app.component.ts / app.routes.ts / app.providers.ts / app-title.strategy.ts   ← type:shell
    (no shell effects left — every orchestrator moved into its own domain's data/;
     app.routes.ts is a `path → loadChildren` table — every domain owns a
     routes/<domain>.routes.ts, tagged type:routes and sealed to its own domain)

  @shared/                                          ← domain:shared
    model/    ( app.types.ts [primitives] + one file per shared concern: base-item ·
                category · item-list · notifications · dashboard · settings ·
                app.consts.ts )                       testing/ (type:testing)
    data/     ( actions/ [dashboard · notifications — the two published contracts —
                          + item-list.actions.factory, the shared event map] ·
                effects/ [persisted-slice + item-list *.factory.ts — the effect builders] ·
                persisted-context.provider — the bounded-context descriptor ·
                boot-hydration.provider · module-hydration.resolver )
    util/     ( db/ [database.service · versioned · migrations] · list/ [list.utils ·
                list.selector · LIST_FACADE] · categories/ · charts/ ·
                item-dialog.service · theme.service · splash.service · pipes )
    ui/       ( base-item/ · categories/ · forms/ · page-header/ )
    feature/  ( list-page — the domain-blind page shell · edit-item-dialog + modal-dialog —
                the two dialog bases · edit-categories-page )

  commlink/ tracking/ office-time/ notifications/ barcode/        ← timetracker domains
    commlink/{data,model,testing}/ = the dashboard read-model + the deck catalog
      and its config slice (two eager slices, both commlink-owned)
  groceries/                                                      ← shopping + storage + products
  tasks/ cash/ trackplay/                                         ← one domain each
  settings/{data,feature}/                                        ← app-global settings (theme) — sealed, eager slice
  geist/{feature,model,util}/                                     ← GEIST — Chrome on-device-model console; NO data/ layer (holds zero NgRx state)
    groceries/feature/{recipes-page,edit-recipe-dialog}/ = SOYKAF, the recipe book
      (the `kitchen` domain is deleted — route path ≠ folder)
    cash/feature/ + trackplay/feature/ = the imperative edit modals (moved out of
      smart-ui, which cannot reach the shared BaseModalDialog)
```

**Inside every `<domain>/data/`** the files are sliced by NgRx role, so a multi-slice domain stays
navigable and all eleven data modules read the same way:

```text
<domain>/data/
  actions/      <slice>.actions.ts             ← one file per action group
  reducer/      <slice>.reducer.ts (+ .spec)
  selectors/    <slice>.selector.ts (+ .spec)
  effects/      <slice>.effects.ts, or <slice>-<role>.effects.ts once a slice has
                more than one (+ .spec)   ← only the domain's OWN effects;
                load/save/telemetry come from the descriptor
  <x>.facade.ts · <domain>.providers.ts · index.ts      ← the DI-facing root
```

**Two kinds of effects, and the casing tells you which.** A domain's hand-written effects are
`@Injectable` **classes** (`TrackingEffects`, `ShoppingEffects`); effects assembled from the shared
builders in `@shared/data/effects/*.factory.ts` are exported as **functional objects**
(`tasksListEffects`, `trackingListEffects`) — because NgRx dedups same-class instances across
injectors, so a shared *class* registered in two lazy contexts would double-dispatch, while every
call of a builder gets its own identities. A role suffix only appears where a slice owns several
effects files (`tracking-list` · `-message` · `-notifications`); a slice with one file is just
`<slice>.effects.ts`, and an *empty* effects class is not a placeholder — it is dead code (the
`ProductsEffects`/`TasksEffects` shells were deleted).

**`data/` holds no pure logic.** A `<slice>.utils.ts` that imports no `@ngrx` is not data — it is
`util`, and it lives in the domain's own **`<domain>/util/`** (`405928e`). `data → util` is a
downward edge Sheriff already permits, so the reducer/selector/effect that consume it read
`../../util/<slice>.utils`. This is also why `@shared/util` carries no `notifications/`: those
transforms had two importers, both in `notifications/data`, so they moved home to
`notifications/util`. `@shared` keeps only what more than one domain actually shares.

`<domain>.providers.ts` declares the context via **`providePersistedContext({...})`** and exports the
resulting `<domain>Context` — a `{ providers, resolve }` bundle the domain's own route manifest
spreads (`...cashContext`) — the same file/shape whether the domain boots eagerly (composed by
`provideAppKernel()`) or per route (handed to a route's `providers`); lifecycle is a property of the
composition site, not of the bundle's name. Sheriff tags come from the two path segments
(`src/app/<domain>/<type>`), so the depth below `data/` carries no boundary — only this convention.

**Sheriff dep rules** (`pnpm exec sheriff verify`): domains sealed (`domain:* → sameTag, domain:shared`). After **sheriff-tighten** there are **no** explicit cross-domain bridges left — every domain is sealed to the default. `barcode` now owns its own `barcode` slice (the SIGIL badge), so the last bridge `barcode→office-time` is gone (§1); the old grocery bridges (`shopping↔storage`, `shopping/storage→globals`) are intra-`groceries` (`sameTag`); `notifications→tracking` and `commlink→…` are inverted behind `@shared` contracts. Type axis: `routes → feature/data/util` (a domain's own route manifest — see Routing), `feature → smart-ui/ui/data/util/model`, `smart-ui → ui/data/util/model` (**strict leaf — no `sameTag`**; a smart component composes dumb UI, never another smart component. The edit-dialog wrappers that compose store-connected sub-components therefore live in `<domain>/feature/`, and `categories-dialog` is rendered by those wrappers instead of nested inside `category-input` — §2. **`@shared` has no `smart-ui` layer** — its last inhabitant became a dumb `ui` component when the `itemDialogs` slice was retired), `ui → util/model`, `data → util/model`, `util → model`. `type:testing` may reach any layer but only `*.spec.ts` may depend on it. Each **`<domain>/data/` is a facade barrel** (`index.ts`): outside code imports the folder (`…/data`) and sees only the public facade (action group · published selectors · the `<domain>Context` bundle · any `ListPageFacade`); reducer/effects/internal selectors are encapsulated (deep import = violation). Other layers stay barrel-less (`enableBarrelLess: true` — per-folder, not global). **`@shared` is layered downward:** `@shared/data` holds only what is genuinely NgRx, itself sliced by role — `actions/` (the two published contracts `DashboardActions`/`NotificationsActions` — both write-**only**, so `@shared/data` has **no `selectors/`**: it names no domain's store key — plus `item-list.actions.factory`, the event map every list-backed context spreads), `effects/` (`persisted-slice.effects.factory` — the functional load/save/telemetry effect builders — plus `item-list.effects.factory`), plus `persisted-context.provider` (the descriptor that composes them into a context bundle), `boot-hydration.provider` + `module-hydration.resolver` (the store root is composed inline in `app.providers.ts`, not a `@shared/data` file; the eager `settings` slice moved out to its own `settings/data` domain). The `ItemDialogService` and the list engine's pure logic sit a layer down in `@shared/util` — they carry no NgRx (`item-dialog.service`, `list.utils`/`list.selector`, `LIST_FACADE`+`IListPageFacade`); a domain's own pure logic sits in its own `<domain>/util/`, never in `data/`. **The `dashboard` read-model is NOT shared** — reducer/selectors/`DashboardFacade`/persistence effects live in `commlink/data`, its types + `summary-` keyspace in `commlink/model`, its fixture in `commlink/testing` (its only readers are the deck + the shell badge); only the telemetry *port* (`DashboardActions.report` + `IDashboardTelemetry` + `createTelemetrySliceEffect`) stayed in `@shared`, which is what keeps suppliers sealed off from `commlink`. The read-model's own `load`/`hydrate` lifecycle is a separate commlink-owned group (`DashboardReadModelActions`, same `'Dashboard'` source string) — `hydrate` carries `IDashboardSummary`, which `@shared` may not name. A domain's `data → @shared` is a downward `data → util`/`model` edge plus the contract edge; `sameTag` on `type:data` otherwise remains only for intra-slice wiring.

**There is no root-state type.** `IAppState` was deleted: every slice is read through its own `createFeatureSelector<ISliceState>('key')` and every facade injects the bare `inject(Store)`; a feature needing several slices recomposes them locally (groceries no longer has to — its aggregates are one slice, so `selectGroceriesState` *is* the cross-list read). A complete root type is impossible by construction — the eager slices (`dashboard`, `settings`, `notifications`) are domain-owned (Sheriff bars `@shared/model` from naming a domain type), every other context is lazy, and `main.ts` may not import `type:model` at all — so the only survivor is the test kit's `TMockKernelState`/`TMockState` (`@shared/testing/test-data`), scoped to what `provideMockStore` seeds by default. Deleting it also made `@shared/model` NgRx-free, so `src/app/@shared/model/app.types.ts` is **no longer** on the eslint `@ngrx` allowlist.

### Routing (`src/app/app.routes.ts` + `<domain>/routes/<domain>.routes.ts`)

Hash routing (`withHashLocation()`). **`app.routes.ts` is a `path → loadChildren` table that names no domain internals** — every domain publishes its own route manifest at `<domain>/routes/<domain>.routes.ts`, which owns that domain's paths, titles, `<domain>Context` spread, facade bindings and `loadComponent`s. The manifest is tagged `domain:<domain>` + **`type:routes`** by the existing `src/app/<domain>/<type>` pattern, so the domain axis seals a domain's routing to its own pages + `@shared` — the shell carries no `domain:` tag and could otherwise reach anything, which is what the old flat table did. Sheriff enforces it on `loadComponent` too, because it collects imports via `ts.preProcessFile`, which reports dynamic `import()`. The manifest deliberately does **not** live in `feature/` (`type:feature` has no `sameTag` since sheriff-tighten §2/§3, so loading a sibling page from there would need that rule re-opened). The `loadChildren` edge being the only shell→domain import is also what finally keeps the eleven data layers **out of the initial chunk** (1.48 → 1.40 MB raw; ≈ 0 on the wire — ngsw prefetches `/*.js` — so the win is boot parse/eval + the seal, not KB).

**Every path is a domain prefix.** Root entries: `commlink` (home/deck), `tracking`, `data/:listId`, `office-time` (+ `/settings`), `settings`, `barcode`, `notifications`, `geist`, `soykaf` (the recipe book), `groceries/*`, `tasks/*`, `cash/*`, `trackplay/*`; `**` → `commlink`. The grocery pages live at **`groceries/{shopping,storage,products,categories}/:listId`** + `groceries/list-settings` (products was `/database`, listId `_products`), and the tasks catalog at **`tasks/categories`** (was `categories/_tasks`) beside `tasks/:listId` — so no cross-domain path ordering is left in the root table; a domain orders its own pages (`cash/rules` before `cash/:accountId`, `tasks/categories` before `tasks/:listId`). Only `/soykaf` and `/data/:listId` deliberately don't read as their folder — they are deck programs, product surfaces rather than structure. **Old pre-prefix URLs are not redirected** (`**` lands them on the deck). `commlink` has a second page, **`/commlink/deck`** — the deck configuration — which `/settings` reaches by a *link*: `settings → commlink` is a domain violation, so the page that edits the deck lives under the deck's owner rather than under the settings prefix.

A manifest spreads its context (`{providers, resolve}` = state + effects + a `moduleHydrationResolver(load, loaded)` that blocks activation until the scoped `loaded` fires) **once on a componentless subtree root** wherever the domain has more than one page there — `groceries` (5 pages: the three lists, the catalog and the flags page — one slice, so there is nothing to co-register), `cash` (6), `trackplay` (5), `tasks` (2), `office-time` (2) — so the slice registers once and `[X] load` fires **once per subtree entry instead of once per page** (Angular reuses a parent whose params don't change; measured: 2 reads per grocery page before, 0 to move between them now). Single-page mounts spread it inline: `tracking`, `data/:listId`, `barcode` (its own single-slice context since sheriff-tighten §1) and `soykaf`, which spreads the same `groceriesContext` as the `/groceries` subtree — recipes are an aggregate of that one slice, and `/soykaf` is its own mount only because it is its own program. `notifications` and the app-global `settings` page are lazy pages over **eager** slices (the inbox; the sealed `settings` domain), so they spread nothing, and `geist` spreads nothing because it has **no slice at all** (its transcript is a component signal — the session lives in the browser, not in our state). Titles via `data.title` on the leaf route + `AppTitleStrategy` (deepest wins, so nesting is transparent).

### State (NgRx)

**NgRx is sealed inside the data layer behind per-domain facades.** No `@ngrx` import lives outside `data/` — every component/shell dispatch and read goes through an `@Injectable({providedIn:'root'})` **`<Domain>Facade`** in `<domain>/data/` (the only place `Store` is injected for that domain's consumers): it exposes state as `selectSignal(...)` signals (route-parameterised reads as factory methods) and commands as `dispatch(...)` methods. Facades: `TrackingListPageFacade`/`TasksListPageFacade`/`GroceryListPageFacade` (these also implement `IListPageFacade`, wired to `LIST_FACADE`) + `ListSettingsFacade`, `CashFacade`, `TrackplayFacade`, `OfficeTimeFacade`, `NotificationsFacade`, `BarcodeFacade`, and the eager, domain-owned `DashboardFacade` (`commlink/data`) + `SettingsFacade` (`settings/data`). **The edit dialogs hold no NgRx state at all:** the draft is a component-local `linkedSignal` and the open-command is one nullable signal on the root `ItemDialogService` (`@shared/util/item-dialog.service`, no `@ngrx` import). The store was the wrong primitive for transient, never-persisted UI state — it cost a duplicated `listId` guard in every lazy orchestrator effect (effects are never torn down), a two-hop action round-trip per open just to derive two label strings, and a per-domain selector + facade signal purely to cast `IBaseItem` back to a domain type. Every open path already started in a facade method holding its list state as a signal, so the seed item is built synchronously there and the three `*-item-dialogs.effects.ts` files are gone, guards and all. `ItemDialogService.open()` copies the item — that is what makes the wrappers' `linkedSignal` draft reseed when the same row is reopened after an aborted edit. The shared `BaseEditItemDialog` reads the command off the host + delegates save/category ops to `void` hooks the subclass wires to its domain facade. **Two dialog lifetimes → two sibling bases in `@shared/feature/`:** `BaseEditItemDialog` for the always-mounted list-item dialogs (nullable draft — it must model "closed"), and `BaseModalDialog` for the imperatively-presented cash/trackplay modals (non-null draft — the component only exists while open; `TForm` is a view-model, not the entity, since those edit mapped fields like cents-as-de-DE-string or signed-amount-as-magnitude+direction). Its `componentProps` id is a signal behind a domain-named setter, which makes `existing`/`draft` reactive and means **no dialog implements `OnInit`**. `cash/…/reconcile-modal`, `cash/…/import-preview-modal` and `trackplay/…/game-settings-popover` stay on plain `ModalController` — they are confirm/preview/popover surfaces with no entity to edit. **Enforced** by an eslint `no-restricted-imports` ban on `@ngrx/*` across `src/app/**`, re-enabled only in `app.providers.ts` (the eager-kernel composition), `**/data/**` (incl. `@shared/data/effects/**`, the generic per-context load/save/telemetry effects), the test kit, and `*.spec.ts` (`main.ts` no longer needs it — it just calls `provideAppKernel()`). Facades are root singletons — a component spec that overrides a selector between two `createComponent` calls must `store.refreshState()` (the signal is shared, not per-instance).

**Three facade file shapes, one rule: the `-page` suffix encodes a token binding, not page-ness.** `<domain>.facade.ts` is the domain's general facade (`CashFacade`, `TrackplayFacade`, `BarcodeFacade`, `OfficeTimeFacade`, `NotificationsFacade`, `SettingsFacade`, `DashboardFacade`); `<aggregate>-page.facade.ts` is reserved for implementations of a **shared page contract token** — `LIST_FACADE`/`CATEGORIES_FACADE` — which is what `GroceryListPageFacade`, `TasksListPageFacade`, `TrackingListPageFacade`, `GroceryCategoriesPageFacade`, `TasksCategoriesPageFacade` and `CashCategoriesPageFacade` all are; and `<aggregate>.facade.ts` is an aggregate facade inside a multi-aggregate domain that binds no token (`RecipesFacade`, `ListSettingsFacade`). Those last two back a page as well, which is exactly why `-page` has to mean the token binding and nothing else. The name's first token follows the **aggregate**, not the domain folder: `GroceryListPageFacade` matches the `grocery-list` multi-list engine, not the `groceries` domain.

The eager kernel is composed by **`provideAppKernel()`** (`src/app/app.providers.ts`, called from `main.ts`): the root `router` reducer (`provideStore`/`provideRouterStore`, composed inline here) plus three eager **domain** bundles that each register from their own `<domain>.providers.ts` — `commlinkContext`, which is `mergeContexts` of **two** slices, `dashboard` (the read-model; a sink every module writes to, badge always-on) and `deck` (see *The deck catalog*), `notifications` (`notificationsContext`; the same argument — a fan-in sink every module publishes into, plus the OS reminder `init()`) and the now-**sealed `settings` domain** (`settingsContext` — the persisted schema `version` anchor **plus the selected UI `theme`**, `TTheme`; `SettingsEffects` mirrors it onto `<html data-theme>` via `theme.service` and lifts the boot splash). Ownership (which domain owns the reducer/effects) and lifecycle (eager vs routed) are independent axes: every domain exports one context bundle from `<domain>.providers.ts`, and whether it is spread into `provideAppKernel()` or into a route is the only difference (the descriptor's `hydrate: 'boot' | 'route'` switches the boot dispatch for a route resolver) — no reducer/effect/action escapes its domain barrel either way, and settings is no longer in `@shared/data`. (`itemDialogs` is **no longer** eager — the slice is gone.) (`listSettings`/`quickadd` are **no longer** eager — they were grocery-specific all along and moved into the lazy `groceries` domain in the settings re-scope; the one app-wide thing they carried, the `version`, became the global `settings` slice.) **Every bounded context except the notification inbox is lazy:** `tracking`, `groceries`, `tasks`, `cash`, `trackplay`, `barcode`, and `officeTime` register per-route via their `<domain>Context` bundle (`<domain>/data/<domain>.providers.ts`) and hydrate in that bundle's `moduleHydrationResolver`, not eager. `groceries` is **one slice** (`state.groceries` = products · shopping · storage · recipes · listSettings, one `npc-groceries` doc, one `[Groceries] load/loaded`), so every grocery route — the lists, the catalog, `/groceries/list-settings` and `/soykaf` — spreads the same bundle; the ephemeral `quickadd` reducer rides along, merged in without a lifecycle because it is never persisted. No global load action — each context owns a scoped `[X] load/loaded` lifecycle and its reducer hydrates on its own `loaded`; each eager domain boots its own hydration via `hydrate: 'boot'` (a `bootHydrationProvider(...)`) inside its own bundle (settings dispatches `SettingsActions.load`, dashboard its read-model load; the theme rides in `settings`) — `main.ts` itself only calls `provideAppKernel()`.

**The deck catalog — one user-configurable list behind the grid AND the side menu.** `DECK_CATALOG` (`commlink/model/deck.catalog.ts`) is every navigable destination — the 13 deck programs plus the two menu-only rows (the deck's own home link, `groceries/list-settings`) — and `CommlinkPage` and `app.component.html` both render from it via `DeckFacade`, neither holding a list of its own. It is **commlink's** because a domain owns the routes it *serves*, not its own presentation in navigation (`groceries` has no opinion about being MARKET, seventh, with a cart icon); per-domain entry manifests would also have forced the shell to import all eleven domains eagerly, undoing the `loadChildren`-only seal. It costs no new coupling either — the shell already imported exactly one domain (`DashboardFacade`). The catalog carries **no label**: codenames are theme-scoped (`deck.<theme>.<id>.name`/`.desc`, resolved in `DeckFacade` against `ThemeService.theme`), so a new theme is a JSON block rather than a code change; the menu keeps its `page-title.*` `titleKey`, because a menu row and its page's title are the same string and only what varies by theme belongs under `deck.*`. `hex` is no longer a field — it is the tile's *slot address*, `$index | hex`, so the top tile always reads `0x01`. The persisted config (`npc-deck`, eager) is three id lists — `order` · `hiddenEntries` · `hiddenModules` — where **absence means default**: a new catalog entry appends and renders, a retired id is ignored on read, so the catalog grows and shrinks with **no migration hop** (only *renaming* an id would need one, so ids are never renamed). `order` is a list rather than an `order: number` per entry because a list IS the order (no renumbering per drop, no gaps, no two entries claiming 3), and a module's flag **cascades at read time and is never written into its entries** — re-enabling a module restores what the user configured underneath instead of flattening it. `SYSOP` is hideable like everything else, which is why the menu toolbar carries a **permanent settings icon button**: without it a user could hide the only door back to the page that un-hides it. Rationale in `docs/dashboard-customization-plan.md`.

**tracking ↔ notifications — how the cross-cutting couplings were resolved:** the background `runningUpdates$` timer was **deleted** (a notification is a point-in-time event, not a live dashboard); the notification CTA **deep-links** (`/notifications` → `/tracking?cmd=<command>&target=<itemId>`, a string route carrying the command the inbox already holds — notifications imports no domain, and the producer resolves the command against its own items instead of looking the row up); tracking **publishes** into the inbox by dispatching the shared `NotificationsActions` and **never reads it** — `project` hands over the complete row set it owns (derived from its items alone) and the reducer merges: rows other owners published are untouched, ones tracking stopped projecting are dropped, and an unchanged `origin.variant` keeps a row's `updatedAt` so a cascade can't drag it to the top. That is what let the shared read half (`@shared/data/selectors`, the kernel naming another domain's store key) be **deleted**; the cost is one idempotent write per tracking mutation instead of a delta computed against foreign state. The always-on notification **badge** still reads the `dashboard` read-model (`selectNotificationsUnread`), not the inbox slice, which keeps the shell domain-blind and gives a cold launch its persisted count.

**There is no toast service.** The published contract's fourth event, `NotificationsActions.toast({ key, params?, color? })`, carries a *transient* message: no reducer reacts, nothing is persisted, and the notifications domain presents it in the one `NotificationsToastEffects` (the only place `ToastController` + the message's `TranslateService.instant` live; it rides `notificationsContext` because a toast can be raised on the eager boot path). Producers therefore describe the message as **data** and stay ignorant of Ionic and of i18n: tracking's five add/update/remove/save reactions became plain dispatching effects, commlink's storage-unavailable fallback emits it next to `hydrate([])`, and the two component-side cases (barcode upload failure, cash "apply rules" result) go through their own domain facade (`reportUploadFailure()`/`reportRulesApplied(count)`) — a component may not dispatch. Trackplay's undo toast is deliberately **not** on this contract: it is an interactive affordance (a button that dispatches `restore`, superseding the previous toast), not a message, so it keeps its own `ToastController` in `trackplay/data`.

**Why the inbox is eager (and `tracking` is not).** `feature/fully-lazy` routed *every* context, notifications included. That forced a second write path — producers had to read-modify-write the persisted `npc-notifications` doc through a `NotificationsStore` port, sharing the reducer's pure transforms so the two paths could not drift — plus a re-hydrate on route entry to correct a slice that could be stale. The port is now **deleted**: a fan-in sink written from every route and read by always-on shell chrome has no route to be scoped to, so it boots in the kernel like the dashboard read-model, and producers just dispatch. `/notifications` is still a lazy *page* (`loadComponent`) — page laziness and slice lifecycle are independent. The lesson: **route a context by its writers, not by its page.**

> **⚠️ lazy ≠ unloaded on exit.** `IonicRouteStrategy` has no `shouldDestroyInjector` and NgRx `provideEffects`/`provideState` have no per-injector teardown, so a lazy route's injector + effects + state register on **first visit and persist for the session** — modules are **not** mutually exclusive. Two lazy modules that subscribe to the **same** action BOTH fire once both are visited (NgRx dedups same-class instances, never different classes) — so each such effect must **guard on the target `listId`** (grocery ∈ `{_storage,_products,_shopping}`, tasks `=== '_tasks'`), reading the same field it routes on. This guard tax is what motivated moving the dialog open-command off the action bus: the three orchestrators existed largely to carry it, and calling `ItemDialogService` directly from each domain facade makes cross-firing structurally impossible. "Lazy" here is a boot-cost win, not memory reclaim.

- **Action-group event keys are camelCase identifiers, not quoted title-case strings** — `addItem:`, never `'Add Item':`. `createActionGroup` camelCases the key to build the creator either way, so the creator names (and every call site) are identical; what changes is the generated `type`, now `[Source] addItem` instead of `[Source] Add Item`. The point is that the wire string and the code you write are the same token, so an action is greppable by the one name it has. **Nothing may match on that string.** Use the creator (`ofType(Actions.addItem)`, `case Actions.addProduct.type:`) — the three hardcoded `case '[Storage] Add Product'` literals in `grocery-list.effects` were the only things the rename broke, which is exactly why they now read `.type` off the creator. Parsing the *source* prefix is still fair game (`listIdByPrefix` reads `[Storage]`), since that is a slice identity rather than an event name.
- **One multi-list engine + shared single-list helpers.** `groceries`' `grocery-list.*` files (actions/selectors/effects, each in its `data/` role folder, plus the pure `grocery-list.utils` in `groceries/util/`) are the multi-list engine (source `[GroceryList]`) — `selectListState` derives the active list from the `:listId` route param via `router.selector` + `stateByListId`. The single-list domains (`tracking`, `tasks`) have **no** separate engine: each owns its slice (`state.tracking`/`state.tasks`) and builds its list flow (add-from-search, sort, search-sync) on the domain-blind `@shared/util/list` helpers (`list.utils`/`list.selector`), driving the shared `ListPageComponent` via its own `*ListPageFacade`. Tracking's former standalone item-list engine (`[ItemList]` shim) + `dialogs` slice were retired onto these shared mechanics + the shared `ItemDialogService` open-command (the last timetracker×kitchen-bot merge-duplicate).
- **Recipe book (SOYKAF) — a fourth grocery aggregate** (`a8c9a74`). `recipes` is a slice of `groceries`, not a domain of its own: a recipe is expressed in the grocery vocabulary (its ingredient lines *reference* `_products` catalog ids, "do I have it" *is* `_storage`), so the matcher reads its siblings via `sameTag` instead of needing a re-opened Sheriff bridge. The match is **half id-based, half name-based** — `IStorageItem` carries no product reference, so the storage half resolves `productId → product.name → a storage row with that name`, and a product rename breaks it until the row follows (see `docs/open-tasks.md`). In the tree: `actions/recipes.actions.ts` · `reducer/recipes.reducer.ts` · `selectors/recipes.selector.ts` · `recipes.facade.ts` (+ the pure matcher one layer down in `groceries/util/recipe-match.utils.ts`), telemetry `source: 'recipes'` + `createMetric('count')` (which flipped the SOYKAF tile standby→online). It has **no context file of its own**: recipes are one of the five aggregates *inside* the `groceries` slice, so they hydrate on `[Groceries] loaded` with their siblings and persist in the same doc — the matcher joins them against products + storage, and being one slice is what makes reading a sibling structurally safe rather than a co-registration rule. The page is `groceries/feature/recipes-page` (+ `edit-recipe-dialog`), loaded by the unchanged `/soykaf` path — **route path ≠ folder**, and the `kitchen` domain is deleted. It deliberately does **not** ride the shared `ListPageComponent`: its rows carry a match verdict, not a name and a swipe. The `/soykaf` route resolves all of them — `mergeContexts` keys each resolver by its slice key, so the merged map cannot collide. `IProduct.alwaysOnHand` (optional, so no migration) is what keeps staples out of the missing count. Decisions + deferred v2 in `docs/open-tasks.md`.
- **Grocery slice renames vs kitchen-bot** (to avoid timetracker collisions): store keys `settings→listSettings`, `dialogs→itemDialogs`; action sources `[Settings]→[ListSettings]`, `[Dialogs]→[ItemDialogs]`, `[ItemList]→[GroceryList]`; types `ISettings→IListSettings`, `IEditItemState→IItemDialogState`, `TDialogsState→TItemDialogsState`. **Settings re-scope:** `listSettings`, `quickadd`, and the quick-add row (`ItemListQuickaddComponent`) now live in the `groceries` domain (they were grocery-specific, not shared); the freed bare `settings`/`[Settings]` names (typed `ISettingsState`, like every other slice) are now the app-global version+theme slice, sealed into its own `settings/data` domain, and timetracker's own settings type/slice/source were renamed `IOfficeTimeSettingsState`/`officeTimeSettings`/`[OfficeTimeSettings]` (later removed entirely — the re-scope left it holding only a dead `showTotalTime` flag, so the whole slice was deleted as dead code). `tasks` dropped its vestigial quick-add entirely.
- **List/dialog orchestrators are per-domain + lazy** (§2b). The old eager shell `grocery-list.effects.ts`/`item-dialogs.effects.ts`/`app.effects.ts` are **deleted**. The grocery multi-list engine lives in `groceries/data/effects/grocery-list.effects.ts` (in `groceriesContext`, scoped to the three grocery lists); `tasks` **and `tracking`** each have their **own switch-free copies** (`tasks/data/effects/tasks-list.effects.ts`; `tracking/data/effects/tracking-list.effects.ts` — both `@shared`-only → sealed; tracking's guard on `listId === '_tracking'`, tasks' on `=== '_tasks'`). The dialog orchestrators are gone entirely — the open-command is a signal service now. Each context's list-flow effects ride in its own bundle's `effects: [...]`, while save + load + telemetry are declared on the descriptor; the inbox's remaining own effects (debug + toast) ride in `notificationsContext` the same way.

### Persistence (`src/app/@shared/util/db/database.service.ts`)

`@ionic/storage-angular`, DB name `np-commlink`, keys namespaced `npc-<slice>` (+ `npc-summary-<source>` for the persisted dashboard read-model). It is a **dumb per-key port**, domain-blind by construction: `bootstrap()` only initializes (init-once guard + schema-version check, no read); each context reads/writes its own key via `load<T>(key)` / `save<K>(key, value)`, or a whole key *family* via `loadPrefixed<T>(prefix)` — commlink's `summary-<source>` docs are the only family, and commlink owns that prefix (`commlink/model`). All four await the init-once guard. Versioning is app-level (`APP_VERSION`, `@shared/model/app.consts`), migration is per-context: every doc is stamped into a `{v,data}` envelope on save and migrated on read by `runMigrations` (`@shared/util/db/versioned.ts`). A context supplies a `ladder` to `providePersistedContext` **only when it has a hop to declare** — the ten always-empty `*.migrations.ts` files are gone and the descriptor defaults it to `[]`. The schema `version` now lives in exactly one place: the eager app-global `settings` slice (`npc-settings`), seeded on first boot by `SettingsEffects` (the per-slice `version`s on `listSettings` + office-time were dropped in the settings re-scope). `quickadd` is ephemeral and **not** persisted (and grocery-owned now); the dialogs hold no store state. `npc-deck` needs no ladder by construction — it stores only entry *ids*, and an unknown one is ignored on read while a missing one takes its default (see *The deck catalog*). Fresh-install only — no migration from the old `np-time-tracker` / kitchen-bot databases.

**No cross-module write port.** `npc-notifications` is written by exactly one thing: the inbox's own `NotificationsSaveEffects`, on every write including a producer's — so a producer dispatches and stays ignorant that notifications are persisted at all (the same arrangement as the dashboard read-model). The `NotificationsStore` read-modify-write port this used to need is deleted; see *Why the inbox is eager* under State.

### i18n

`@ngx-translate/core`, German default. Flat dotted keys. **All kitchen-bot keys are namespaced under `grocery.`** (`public/i18n/{de,en}.json`) to avoid collisions with timetracker keys. TS keys not used via the `translate` pipe must be `marker('grocery.…')`.

**Page titles are the one namespace keyed by page, not by domain: `page-title.<domain>[-<page>]`** — `page-title.cash`, `page-title.cash-rules`, `page-title.groceries-shopping`, `page-title.trackplay-games`, `page-title.office-time-settings`, `page-title.categories`. A title is read by the shell (`AppTitleStrategy`, the side menu) as much as by its page, so it lives in one flat namespace rather than under five different domain prefixes — which is also what retired `officetime.` (≠ the `office-time` domain), the `cash.`/`trackplay.` title prefixes, and tasks' title hiding under `grocery.`.

### Types

**Sliced by concern, never a god file — and never a barrel: `<domain>/model/<concern>.types.ts` everywhere.** Every model layer now reads the same way: `cash` splits into `account`/`transaction`/`rule`/`cash.types`, `groceries` into `grocery-list`/`recipe`/`list-settings`/`groceries.types`, and a domain whose model is one tightly-coupled concern keeps one file named for it (`barcode.types`, `tracking.types`, `task.types`, `trackplay.types`, `office-time.types`, commlink's `dashboard.types`). The `model/index.ts` barrels are gone, so an import line names the vocabulary it uses instead of the folder; a `*.consts.ts` appears only where there is a body of constants (`geist`), not for a domain's one list-id.

In `@shared/model`, `app.types.ts` keeps only the primitives every layer speaks (`TMarker`/`TTimestamp`/`TColor`/`TTheme`/`TIonDragEvent`); each shared concept owns a file next to it — `base-item.types` (`IBaseItem`/`TUpdateDTO`/`TEditItemMode`), `category.types`, `item-list.types`, `notifications.types` (the inbox shapes **plus** the `IToastMessage` contract), `dashboard.types`, `settings.types`. The layer is **barrel-less** (Sheriff `enableBarrelLess`), so import the concern's file directly — which is what makes an import line say which shared vocabulary a file actually depends on. `IItemList<T>` requires `categories`/`mode` (grocery reads them unguarded; the tracking list carries empty defaults). There is no shared datastore type: `DatabaseService` is generic over the caller's `T` (see Persistence).

### Capacitor / Android / two barcodes

`appId np.afterwork.commlink`, `webDir www/browser`. Plugins: the timetracker set + `@capacitor-mlkit/barcode-scanning`. **Two unrelated "barcode" features:** `barcode/` (SIGIL — displays an uploaded badge image, no camera) and `groceries/util/barcode-scanner.service.ts` (mlkit EAN-13 camera scanner, wired to a native-guarded scan button on the shopping/storage pages → feeds `GroceryListPageFacade.showCreateProductFromScan`, which is also why it lives in `groceries`, not `@shared`). The `android/` folder is **git-ignored and regenerated on demand** (not committed): `npx cap add android` once per machine, then `pnpm run build:android` (= web build → `cap sync android` → `./scripts/android-postsync.sh`) for every rebuild. The postsync step re-applies the edits Capacitor strips on every sync — the mlkit `barcode_ui` `meta-data` + `CAMERA`/`FLASHLIGHT`/`POST_NOTIFICATIONS` permissions, and `versionName 1.0.0`/`versionCode 1`. The script is idempotent. The generated activity `configChanges` is already the rich Capacitor-8 set, so it needs no augmentation.

**GEIST is web-desktop-only, by design.** `@shared/util/language-model.service.ts` wraps **Chrome's built-in Prompt API** (Gemini Nano, on-device — no key, no network per prompt), which exists in desktop Chrome 148+ and **not** in Chrome for Android, iOS, or the Android System WebView Capacitor renders into. So `unavailable` is a permanent, expected outcome on the APK target, not an error: the page renders its NO RESONANCE explainer instead of a dead prompt, and the deck tile goes dark. **There is deliberately no synchronous `isSupported`** — the `LanguageModel` global is exposed on *any* secure http(s) origin, including browsers with no model behind it (headless Chromium reports `downloadable`), so its presence says nothing about whether a prompt can be answered. The service therefore probes `availability()` **once**, memoized, and publishes it as a signal both readers share: the page drives its own link state machine off it, and `CommlinkPage` maps it through `LANGUAGE_MODEL_STATUS` (`available` → online · `downloadable`/`downloading`/`probing` → standby · `unavailable` → **offline**), which is why `onlineCount` had to become a `computed` — a capability resolves after first paint. Build wiring is easy to miss — the ambient globals come from the `@types/dom-chromium-ai` devDependency, which must be listed explicitly in `tsconfig.{app,spec}.json` `types` (this project opts out of auto-inclusion), plus `DOM.AsyncIterable` in the root `lib` for `promptStreaming`. Streamed answers render in a `<pre>`: the model's newlines are meaningful and `<pre>` is the one element whose whitespace Prettier will not reflow. No e2e — the happy path is unreachable from headless Chromium and the module is an experiment.

## Theming — two themes (Cyberpunk deck + OK Boomer)

**Two** themes off one token group: **cyberpunk** — the Shadowrun deck (near-black slate, amber + teal neon, monospace, glow, HUD frame; the **default**) — and **OK Boomer** — a plain, light, serious office look (sans-serif, flat surfaces, sentence case, no neon). **Do not restyle components one by one** — retheme the CSS custom properties. The active theme is the **`<html data-theme>`** attribute (default `cyberpunk`), driven by the eager `settings` slice (`selectTheme` · `SettingsActions.setTheme` · picker on `/settings`) and applied by `SettingsEffects.applyTheme$` via `@shared/util/theme.service` (also sets `<meta theme-color>` + native status-bar style). The async boot read is covered by a boot **splash** (`@shared/util/splash.service` + `index.html #app-splash` on web / `@capacitor/splash-screen` `launchAutoHide:false` on native) revealed once the theme is applied — so the theme resolves before first paint, no flash. Plan/rationale: `docs/theming-two-themes-plan.md`.

- **Plain = base, cyberpunk = opt-in.** `src/theme/_shadowrun.scss` owns the `--sr-*` palette + `src/theme/variables.scss` the Ionic `--ion-*` chrome; the **base `:root` holds the plain OK-Boomer values**, and the amber/teal-on-slate deck values live under **`:root[data-theme='cyberpunk']`** (so a new surface reads plain unless it opts in — "serious looks serious" by construction). **"Flip" tokens** turn structural axes into per-theme values so components reference a token, never a literal: `--sr-deck-font` (sans↔mono), `--sr-heading`/`label`/`brand-transform` + `-tracking` (case + spacing), `--sr-radius`, `--sr-glow`/`-lg` (→ `none` in plain). Component SCSS must use these tokens (not hardcoded `uppercase`/`letter-spacing`/`--sr-mono`); purely-decorative effects (glitch, grid overlay, scanlines, LED glow, hud gradient/bevel) are gated under `:root[data-theme='cyberpunk']` / `:host-context([data-theme='cyberpunk'])`. Every surface is uniform amber (`primary`) / teal (`secondary`); `TColor` (`@shared/types.ts`) is Ionic's base palette. `@use`d once from `src/global.scss` (which also carries the Android safe-area map + `body.scanner-active` transparency).
- Deck signature pieces are **theme-aware Sass mixins** in the side-effect-free `src/theme/_deck.scss`: `panel-base` (flat) vs `panel-cyber` (gradient+bevel), `led-base` (solid dot) vs `led-glow` (bloom+pulse), `hud-corners`, `brand`; `_shadowrun.scss` wraps them as the global `.sr-panel`/`.sr-corners`/`.sr-led*`/`.sr-brand*` classes (base emitted always, cyber variant under the deck selector). Consume via `var(--sr-*)` / the `.sr-*` classes, or `@use 'theme/deck'` + `@include` where a class can't reach (`:host`/pseudo-elements); **never `@use 'theme/shadowrun'` from a component** (it emits global CSS).
- `/commlink` deck is the reference cyberpunk expression; `/soykaf`, `/geist`, `/trackplay`, and the grocery/office-time pages all read the same shared classes. The programs render as HUD tiles from the **user-configurable catalog** (below) rather than a hardcoded array, so the grid's tile count is whatever that user shows — the status strip still reports the grid's full complement (`DECK_SLOT_COUNT`, 13), because hiding a program is a navigation choice, not an uninstall. SOYKAF is `online` now that the recipe book replaced its stub, so **GEIST is the only capability-gated one**: `CommlinkPage.status(p)` reports a `needsLanguageModel` program's *capability* status instead of its declared one (`standby` while the weights still need downloading, `offline` where the on-device model can never exist), keeping it out of the loaded count either way, so the deck never advertises a program that cannot run there.
- **Adding a third theme** = add plain-relative values on the base `:root`, a `:root[data-theme='<name>']` override block (Ionic `--ion-color-*` + `--sr-*` + flip tokens), a `TTheme` union member, a picker option, **and a full `deck.<theme>.<id>.name`/`.desc` block** (`deck.catalog.spec.ts` fails the build otherwise — `translate` renders the raw key on a miss). `theme/palettes/_example.scss` is the older `.ion-palette-<name>` seam reference (superseded by `data-theme`) — do **not** import Ionic's prebuilt `dark.class.css`.
- **Re-skin audit — done.** The grocery/cash dialog clipping (shared form inputs on `labelPlacement="stacked"`), the chart palettes (tokenised via `@shared/util/charts/chart-colors` reading the live theme tokens; `_charts.scss` on `--ion-color-*`/`--sr-*`), and the last hardcoded German button labels (moved to i18n) are all resolved. `docs/open-tasks.md` carries anything still genuinely open.
